## 已驗證結論

隔離 Simulator 三次完全終止後再啟動，錄影均出現約 **7.6–8.0 秒白畫面**。首屏逐股讀取歷史 Trade 的日期／價格，是目前量到的最大成本：16 股、21,615 筆，約 **5.35–5.54 秒**，全在主執行緒。細分後其中 **5.393 秒**用在 SwiftData 模型欄位取值與陣列建立；窗口日期算法本身只有 **0.035 秒**，觀察註冊約 **0.057 秒**。

`ModelContainer` 開啟僅 **0.027–0.055 秒**。此資料已是 T4/S65，停用自動更新的兩輪也重現相近空白，沒有證據將本次主要延遲歸因於 schema migration、T/S 重算或行情下載。這是 Mac Simulator 證據，不是使用者實機秒數；真實裝置的硬體、資料量及方向可能改變占比。

## 程序順序與首屏界線

1. `simStock3App.sharedModelContainer` 同步建立 Schema、ModelConfiguration、ModelContainer（`simStock3App.swift:91`）。正常根畫面依賴其完成。
2. 根畫面 `StateObject` 建立 `uiObject`，再建立 `simObject`／`Technical`（`uiObject.swift:241`、`simObject.swift:184`）。其中載入大盤快照、讀股票名錄及群組、初始化偏好設定，再逐股核對人工操作摘要。這些都是每次冷啟動的同步路徑。
3. `viewList` 的 `@Query` 及首屏列開始求值。價格圖示的 `Trade.isBeforeSimulationStart`、績效的 years 等會讀 `Stock.effectiveSimulationStart`，進入 `CalculationWindowAccess.swift:12`。`cachedCalculationWindow` 是記憶體狀態，冷啟動不存在；程式取得 `stock.trades`、讀全部日期／價格、建立窗口並註冊逐列觀察。
4. root `onAppear`／`.task` 在約 1.49–1.58 秒已被呼叫，**此時錄影仍白畫面**。所以不能把 `onAppear` 當成首幀。各股窗口工作接著延續到約 7.6–7.9 秒；首次可見清單由錄影確認。
5. 一般流程在清單可見後繼續底部資料檢查。本輪因網路被診斷 URLProtocol 阻擋，屬離線情境；其正式資料檢查約 3.18 秒、整輪約 3.42 秒，與先前白畫面分開。這不是正常網路的完整效能驗收。

已發布 IPA 的 `UILaunchScreen` 為空字典，沒有自訂內容。Release 的正常根畫面也沒有刻意顯示透明等待頁；`Color.clear` 只屬 DEBUG unit-test host。錄影可確認「白畫面→完整清單→底部檢查」；白畫面中 OS 啟動畫面與可能已提交的空白 app surface 之精確交接時刻，尚未用系統 compositor trace 證實，不由外觀猜定。明確的事實是首個有內容畫面尚未準備完成，主執行緒正執行上述工作。

## 改善方向與最低下一步

後續使用者已指定先盤點並設計任務，優先簡化 query，而非先新增持久窗口摘要。現行下一步是[改善計畫 P1](冷啟動查詢與啟動畫面改善計畫-20261023.md#6-改善任務順序相依與完成界線)：有條件的已入群股票查詢、窗口首末有效價 limit 1、最新列共用及輸入事件失效，消除首屏與橫式明細的全關聯觀察；再依實際 SQL 驗證索引。日期與保存資料範圍的精確對照、上市例外及索引證據見計畫，不將 `dateFirst` 與 `dateRequestStart` 混用。

目前只能證明成本集中在欄位取值，尚未以 stack sample 區分 Core Data fault materialization、欄位解碼或其他 accessor 內部成本。日期算法不是優先優化對象。單加啟動畫面或把工作移到首幀後，可改變等待外觀，但不等於縮短總工作。啟動圖檔已依後續授權製作，白底 v2 圖稿已由使用者採用；Launch Screen 與 app 初始銜接畫面沿用相同版式，尚未接入 App。**產品實作與發布仍未授權；三次量測沿用，沒有重跑。**
