# 候選回測自動化

一般固定三年候選回測統一使用 [`scripts/run-candidate-backtest.sh`](../scripts/run-candidate-backtest.sh)。這裡的「一鍵」是把容易出錯的外層操作集中成單一命令；候選規則的設計、Swift 候選掛勾與每個下一樣本的授權仍然分開處理。

## 適用範圍

- 已在 Debug App 實作、且已獲核准的單一候選。
- A／B／C／D 中一次只跑一個明確樣本。
- 正式 Baseline 已有完整 DecisionBase。
- 一般固定三年候選；不取代全期間壓力測試、正式 Baseline 建立或發布流程。

腳本不會自行產生規則、接著執行下一樣本、採用候選、commit 或 push。

## 執行方式

```bash
scripts/run-candidate-backtest.sh \
  --candidate-id nr2A2 \
  --candidate-flag --candidate-nr2-a2 \
  --sample A \
  --rule-commit 73003cf8f39cbf3a673792957324f508261bd731
```

- `candidate-id` 預期應對應 `DecisionDelta` 使用的穩定 ID；若命名在實作版本中與 `candidate-id` 別名不同（例如 `NR8-S1-C` 實際以 `st02fAdd120` 寫入 DecisionDelta），本腳本會改為以 `decision-summary.json` 的 `candidateID` 與 `sampleID` 對齊完成標記，避免 `candidate-id`/資料夾命名差異造成 timeout。
- `candidate-flag` 是已實作的 Debug 啟動參數。
- `rule-commit` 是正式 Baseline／DecisionBase 的規則 commit，不是未提交候選的工作樹名稱。
- 預設使用 13 吋基準裝置 `iPad Pro 13-inch (M5)`；可用 `--simulator-name` 暫時指定其他裝置。
- 同名本機輸出已存在時預設停止；確認是同候選安全重跑後才使用 `--replace-output`，舊輸出會改名保留而不直接刪除。

## 自動完成的工作

1. 確認正式規則 commit 存在，解析指定 Simulator 的 UDID。
2. 啟動 Simulator、建置 Debug App，從建置產物讀取實際 bundle ID。
3. 覆蓋安裝而不刪除 App 資料，安裝後重新取得資料容器。
4. 依 Sample 與完整規則 commit 唯一定位專案端正式 DecisionBase，要求 `.complete`、`.p4b-complete` 與 SQLite 完整，再以暫存目錄同步至目前 App 資料容器；不信任 Simulator 先前殘留副本。
5. 終止舊 PID，再以固定三年、摘要模式及 DecisionDelta 參數啟動唯一核准樣本。
6. 等候與本次 candidate ID／Sample 相符的新 `.complete`，不以固定短逾時誤判正常運算。
7. 從 `decision-summary.json` 反查真正的 run ID 與 DecisionBase ID，並核對它就是本次同步的正式基底，不手工猜測輸出路徑。
8. 核對 run ID 確實是 `fixed3y`，並要求 `baseline.json`、`manifest.json`、`periods.csv` 齊全。
9. 搬到 `exports/backtest-candidate-runs/` 與 `exports/backtest-decision-deltas/`。
10. 產生 `run-summary.md`，檢查輸出身分、分數算術、前置狀態、SQLite 完整性、異常值、資金不足與非正常股票狀態。

若建置或回測失敗，腳本保留建置紀錄與最近輸出清單；Simulator 維持開機，方便直接診斷。完成後也保持 Simulator 開機。

## 判讀界線

`run-summary.md` 只是可靠的第一層摘要，列出正式 Baseline／候選雙方分數、股群、受影響窗口、DecisionDelta 與集中度。它不能自行判定採用、放棄或下一樣本；仍須依 [`doc/現行回測規則.md`](現行回測規則.md)及 [`doc/回測規則驗證.md`](回測規則驗證.md)完成股票窗口、ROI、週期、資金與直接決策分析。
