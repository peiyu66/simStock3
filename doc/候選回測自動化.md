# 候選回測自動化

一般固定三年候選回測統一使用 [`scripts/run-candidate-backtest.sh`](../scripts/run-candidate-backtest.sh)。這裡的「一鍵」是把容易出錯的外層操作集中成單一命令；候選規則的設計、Swift 候選掛勾與每個下一樣本的授權仍然分開處理。

## HN06A-V29-R1 已結案的研究入口

[R1已結案](回測規則驗證.md#hn06a-v29-r1-closed)，A～D完整移除對照後不採用、不送E、不跑九年；R1專用Debug接線已移除，正式H-N06a保留。歷史旗標 `--candidate-hn06a-v29-r1`／`--candidate-hn06a-v29-r1-control` 與候選ID `HN06A-V29-R1`／`HN06A-V29-R1-CONTROL` 不再作為目前可執行入口。

保留v29／v15／T3/S48及完整規則commit的[A／B原完成清單](../exports/hn06a-v29-r1-review-20260910/completion.json)、[C／D完成清單](../exports/hn06a-v29-r1-cd-review-20260910/completion.json)與[清理核對](../exports/hn06a-v29-r1-closure-20260910/closure.json)。歷史重現須使用相應凍結來源及另行授權，不能用已移除旗標直接執行現行App，也不能用舊H42a／S8代替本輪。原App及正式瀏覽資料已恢復，沒有待續程序。

HN01A-H9-S2 已停止，不送 E、不採用；已完成 A～D 固定三年及分析，對照 v29／DecisionBase v15／T3/S48；[停止決定與 H-N01b 補查](回測規則驗證.md#hn01b-v29-d0-ab)為目前進度來源。旗標 `--candidate-hn01a-h9-s2` 使用候選 ID `HN01A-H9-S2`；S1 與已合格 A 控制仍保留，S1 控制用明確辨識的 `--candidate-hn01a-h9-s1-control`／`HN01A-H9-S1-CONTROL`，不加 runner 的通用 `--control`。S2 與 S1／控制使用獨立 run ID，均保留三窗 store；未支援全期間。未帶候選旗標時維持正式規則。研究完成後已恢復原正式 App 及瀏覽副本。

下方v27及更早的系列紀錄保留其歷史版本身分，不作現行Baseline入口。

## 適用範圍

RP-S03 已採用為 S-P09，SN01-L9-S5 已採用為 S-N01c，HP04-H9-S4 已納入 H-P04，LP03-FLAT-GT-S5 已納入 L-P03，LP10-HELD-NONFLAT-H9-S5 已納入 L-P10；LP06 維持原規則並結案。這些系列的歷史候選入口均停止接受新執行，重現須使用原規則 commit 或候選封存來源。新正式 Baseline 使用 [`run-formal-recovery-low-baseline-v27.sh`](../scripts/run-formal-recovery-low-baseline-v27.sh)，須明確提供已提交的完整規則 commit；不因此授權其他候選或發布。

正式流程依序建立 A～E 的固定三年與全期間報告、DecisionBase v13 與 P4b；兩種期間均須與已採用 LP10-HELD-NONFLAT-H9-S5 的 periods.csv 逐位一致，並對照 v26。大盤開高低收、價格階段與九日極值共用凍結來源，先核對 SHA-256；一般候選也同步這些正式規則必需的輸入。舊報告與未完成產物不覆寫，遇到完成標記不符、App 失敗或裝置停止即保留現場診斷。

- 已在 Debug App 實作、且已獲核准的單一候選。
- A／B／C／D／E 中一次只跑一個明確樣本；E 是全弱勢壓力樣本，不把甲／乙組誤讀成較強／較弱股群。
- 正式 Baseline 已有完整 DecisionBase。
- 一般固定三年候選；不取代全期間壓力測試、正式 Baseline 建立或發布流程。

腳本不會自行產生規則、接著執行下一樣本、採用候選、commit 或 push。

## 執行方式

```bash
scripts/run-candidate-backtest.sh \
  --candidate-id nr2A2 \
  --candidate-flag --candidate-nr2-a2 \
  --sample A \
  --rule-commit 73003cf8f39cbf3a673792957324f508261bd731
```

- `candidate-id` 預期應對應 `DecisionDelta` 使用的穩定 ID；若命名在實作版本中與 `candidate-id` 別名不同（例如 `NR8-S1-C` 實際以 `st02fAdd120` 寫入 DecisionDelta），本腳本會改為以 `decision-summary.json` 的 `candidateID` 與 `sampleID` 對齊完成標記，避免 `candidate-id`/資料夾命名差異造成 timeout。
- `candidate-flag` 是已實作的 Debug 啟動參數。
- `rule-commit` 是正式 Baseline／DecisionBase 的規則 commit，不是未提交候選的工作樹名稱。
- 預設使用 13 吋基準裝置 `iPad Pro 13-inch (M5)`；可用 `--simulator-name` 暫時指定其他裝置。
- 同名本機輸出已存在時預設停止；確認是同候選安全重跑後才使用 `--replace-output`，舊輸出會改名保留而不直接刪除。

## 自動完成的工作

1. 確認正式規則 commit 存在，解析指定 Simulator 的 UDID。
2. 啟動 Simulator、建置 Debug App，從建置產物讀取實際 bundle ID。
3. 覆蓋安裝而不刪除 App 資料，安裝後重新取得資料容器。
4. 依 Sample 與完整規則 commit 唯一定位專案端正式 DecisionBase，要求 `.complete`、`.p4b-complete` 與 SQLite 完整，再以暫存目錄同步至目前 App 資料容器；不信任 Simulator 先前殘留副本。
5. 終止舊 PID，再以固定三年、摘要模式及 DecisionDelta 參數啟動唯一核准樣本。
6. 等候與本次 candidate ID／Sample 相符的新 `.complete`；正常運算不以固定短逾時誤判，但 App 若寫出 `.last-run-failure.txt`，或 Simulator 在等待期間不再是 Booted，立即回報實際錯誤或列出最近產物並失敗，不盲等到總逾時。
7. 從 `decision-summary.json` 反查真正的 run ID 與 DecisionBase ID，並核對它就是本次同步的正式基底，不手工猜測輸出路徑。
8. 核對 run ID 確實是 `fixed3y`，並要求 `baseline.json`、`manifest.json`、`periods.csv` 齊全。
9. 搬到 `exports/backtest-candidate-runs/` 與 `exports/backtest-decision-deltas/`。
10. 產生 `run-summary.md`，檢查輸出身分、分數算術、前置狀態、SQLite 完整性、異常值、資金不足與非正常股票狀態。

若建置或回測失敗，腳本保留建置紀錄與最近輸出清單；Simulator 維持開機，方便直接診斷。完成後也保持 Simulator 開機。

內部回測畫面捕捉到錯誤時，會同步把完整的「回測失敗」訊息寫入 App Documents 的 `.last-run-failure.txt`；runner 每次啟動前清除此輪專用舊標記，等待時持續檢查。這可辨識「App 仍在前景但工作已失敗」的狀況，例如候選旗標尚未登錄而被誤判為 Baseline，不必等到總逾時才由畫面人工發現。

若輸出只停在部分 `period-*.store`、沒有 DecisionDelta 完成標記，同時 `simctl` 顯示目標 Simulator 已是 Shutdown，代表回播已失去執行環境，不是仍可等待的慢速階段。保留該次建置 log 與部分產物，重新啟動裝置後重跑同一個已核准候選；專案端若已有同名完整輸出才加 `--replace-output`，只有 Simulator 容器內的未完成目錄不視為可比較結果。

## 判讀界線

S45 採用後，LP06／LP10 歷史研究入口停用；不能用現行正式規則冒充候選。採用前 Swift 來源保存在 `exports/lp10-adoption-source-20260908/`，既有報告不改寫。

歷史 `LP10-HELD-H9-S4` 曾支援 `--full-window-stress`：使用獨立 `9y-fullstress` run ID、T3/S44、策略 `s37-candidate-lp10-held-h9-s4`，對照同 Sample 的 v26 全期間。沿用固定窗口的候選條件，只做 score-only，不建立 DecisionBase／DecisionDelta；每個樣本仍需授權，使用者一次核准 A～E 時可依序完成。九年結果用於路徑及資金風險，不自動取代固定窗口採用權重。

歷史 `LP10-HELD-NONFLAT-H9-S5` 同樣曾支援此入口，使用獨立 S5 `9y-fullstress` run ID、T3/S44、策略 `s37-candidate-lp10-held-nonflat-h9-s5`，對照相同 Sample 的 v26 全期間。S5 固定窗口及計分不變；除了逐日負結餘，也比較買賣／持股變化與期末連續空手交易日數，避免只用期末分數推定沒有停止交易。

全期間摘要除本金不足旗標外，須逐日掃描候選及正式 `browse.store` 的負結餘（低於 -0.01 元，排除浮點尾差），包含持股與空手列，列出股票、最低結餘、日期範圍及筆數。只要任一邊存在負結餘，摘要工具先保存報告，再以退出碼 2 停止 runner 的成功流程；`.complete` 仍表示回測產物完成，不表示資金安全通過。先檢查已保存的報告，不重跑，也不以補錢或修改本金收回語意消除警示。S4-E 鴻準曾因收回加碼本金後負結餘而無法買入，卻沒有設置本金不足旗標，是這項檢查的回歸案例。

歷史 `LP03-FLAT-GT-S2` 曾支援 `--full-window-stress`：另建 `9y-fullstress` run ID，資料 T3/S43、候選策略 `s36-candidate-lp03-flat-gt-s2`，對照同 Sample 的 v25 全期間。只產生 score-only 結果，不建立全期間 DecisionBase／DecisionDelta。

歷史 `LP03-FLAT-GT-S5` 使用相同流程、候選策略 `s36-candidate-lp03-flat-gt-s5` 及 `flat-grade-or-low-entry` run ID，資料與參考為 T3/S43／v25。S5 正式採用後，整個 LP03-FLAT 系列入口停用；本機候選來源保存在 `exports/lp03-adoption-source-20260908/`，既有報告不改寫，不能以 S44 冒充原候選。

`run-summary.md` 只是可靠的第一層摘要，列出正式 Baseline／候選雙方分數、股群、受影響窗口、DecisionDelta 與集中度。它不能自行判定採用、放棄或下一樣本；仍須依 [`doc/現行回測規則.md`](現行回測規則.md)及 [`doc/回測規則驗證.md`](回測規則驗證.md)完成股票窗口、ROI、週期、資金與直接決策分析。

全期間 score-only 壓力測試不產生 DecisionBase／DecisionDelta；App 的結構化產物位於 `Documents/InternalBacktest/Runs/<run-id>/`。`MKT-PP-S02`、RP-S03、SN01-L9-S4 曾支援 `--full-window-stress`，均須依各自歷史程式版本重現，不能用新版正式規則冒充舊候選。此模式禁止控制組及尚未接線的候選，依候選核對 run ID、`T/S`、規則版本及正式全期間參考報告，再檢查 `.complete`、manifest、`browse.store` 與摘要，不讀固定候選的 DecisionDelta。若進度可疑，先檢查同一 run ID 的失敗標記及最近產物，不盲等。

S4 當時的全期間入口使用獨立 `9y-fullstress` run ID，對照同 Sample 的 v23／T3/S41；原固定三年 run ID 與候選條件不變。這段保留為歷史流程，S-N01c 採用後不再啟用。

歷史 `HP04-H9-S4` 的 `--full-window-stress` 使用獨立 `9y-fullstress` run ID、`T3/S42` 及 `s35-candidate-hp04-h9-s4`，對照同 Sample 的正式 v24 全期間。正式納入 H-P04 後也停用此候選入口，僅供依封存程式重現；不產生全期間 DecisionBase／DecisionDelta。
