# 候選回測自動化

一般固定三年候選回測統一使用 [`scripts/run-candidate-backtest.sh`](../scripts/run-candidate-backtest.sh)。這裡的「一鍵」是把容易出錯的外層操作集中成單一命令；候選規則的設計、Swift 候選掛勾與每個下一樣本的授權仍然分開處理。

<a id="task-execution-procedure"></a>
## 專案、研究與檢驗的共用程序

本節適用於本專案的文件維護、既有資料診斷、研究、App 與資料檢驗；下方 runner 命令只適用於候選回測，不因共用程序而要求所有任務跑回測。這是 2026/09/17 核准的既有約定整併，不新增策略、樣本、採用或發布授權，也不代表 runner 已新增自動防護。

### 開始：範圍與完成條件

先依 [AGENTS.md](../AGENTS.md) 的起始閱讀路由定位當次授權、要回答的問題、輸入與預期成果；分清原任務待續及僅討論的提案。已有有效授權就接續，不因換交談重複請示。若預估須擴張成額外任務，先說明新增段落、資源成本與能解鎖的決策，核准後才擴張。

按任務套用[版本核對](#research-version-preflight)，決定是否需建置、覆蓋安裝或重播。純文件工作只查相關差異、定義、狀態與連結；既有報告診斷先重用合格來源，不為形式啟動 Simulator 或重建資料。先確定什麼證據足以完成本次問題，再執行相稱檢查；不新增逐任務必填的大型檢查表。

<a id="execution-progress-recovery"></a>
### 執行：進度、失敗與恢復

- **進度以實際工作為準。** 長任務須有持續更新的階段、處理對象、日誌、分段成果或可靠新產物。程序仍存在、App 仍在前景、尚未到逾時都不等於工作有前進；耗時可疑、進度停止或與預期階段不符時，立即中斷盲等並保留現場診斷。正常有進度的運算不以固定短逾時誤判，也不恢復舊有「可等約 30 分鐘」的容許基準。
- **失敗即時回報。** 說明失敗階段、實際錯誤、已完成範圍及下一個診斷動作；保存本批身分、最後可靠產物與必要日誌，不以舊完成標記或部分輸出宣稱成功。只暫停依賴問題的步驟，其餘已核准且可獨立的工作繼續。
- **重試須有依據。** 區分輸入／版本、接線／前態、預期路徑差異、runner／產物完整性及非決定性問題。可預期的路徑銜接、格式轉換、隔離副本與安全修復在原授權內自主完成；先處理原因再重跑受影響檢查，不原樣反覆啟動。候選控制未恢復合格前，不接受報告或解讀研究結果。
- **保存恢復方式。** 修復後補正相關 runner／完成標記／失敗偵測，或在既有任務紀錄留下根因、可疑訊號與恢復方式；根因未確認就如實標記。若涉及顯著擴張範圍／額度、改變設計、正常資料可能受損或未揭露的重大風險，先提出影響並確認，不藉修復新增專案。

<a id="simulator-screen-recovery"></a>
### 檢驗環境：螢幕睡眠與鎖定

使用者已決定自行停用 Mac 螢幕保護。「螢幕睡眠」指顯示器休眠，與整台 Mac 睡眠不同；它可能依系統設定伴隨鎖定，不能互相等同。這項約定不授權更改密碼或停用安全保護。

遇到螢幕睡眠或鎖定，先使用已啟用的 Computer Use／Locked Use 正常喚醒與自動解鎖流程。首次失敗**立即回報**，再等約 5 秒重試一次；仍失敗便回報阻擋、請使用者手動解鎖，不反覆盲試或繞過安全機制。這個短暫重試只處理畫面喚醒可能的過渡狀態，不套用到資料錯誤、認證拒絕或所有長時間作業。

重新取得當次工具說明與 UI 狀態後，依最新元素操作，不沿用失效的 handle 或 element ID。工具回報「已鎖定」不獨立證明需要密碼；回報應區分使用者觀察、工具訊息及實際操作結果。已驗證的螢幕測試範圍見 [2026/09/17 測試補記](工作交接.md#screen-state-test-20260917)，不將單次成功推論為所有系統版本均可靠。

<a id="verification-completion"></a>
### 檢驗與收尾：證據及狀態

| 確認層次 | 足以支持的結論 | 不能直接推論 |
| --- | --- | --- |
| 程序／裝置狀態 | 指定 PID 或裝置正在運行 | App 畫面可讀、可操作或工作完成 |
| 畫面讀取 | 取得當次 App 畫面／可及性內容 | 點按有效或鎖定時冷啟動成功 |
| 實際操作 | 執行核准操作後，讀到對應狀態變更 | 全部功能、資料遷移或歷史重播通過 |
| 資料／研究驗證 | 本批來源、完成條件及必要結果核對通過 | 候選已採用、已 commit、push 或發布 |

只做當次所需層次；未測試的冷啟動、版號、資料完整性或其他情境明示未驗證。資料檢驗先列預期可變項目（例如正常 Yahoo 當日更新），再查非預期變更；保持 App／store 不被替換不等於內容完全不變。依[版本核對](#research-version-preflight)確認本批輸出身分，既有完成標記不單獨代表結果有效。

完成或受阻時，在既有研究 README、protocol／sources 或專題進度中保存必要證據，不為本程序另建平行狀態表。回報已完成、未驗證、已授權待續與阻擋；實作、檢驗、採用、commit、push、發布分開描述，未查即時遠端就不宣稱遠端一致。

依[文件狀態日常維護](README.md#document-status-maintenance)同步本次涉及的正式來源與索引；接手資訊有變才更新[工作交接](工作交接.md)。日常進度不建立歷史快照，正式移交才依既有交接程序保存不可回寫的快照。Git／發布依 [AGENTS.md](../AGENTS.md#git-與發布) 與[發布流程](發布流程.md)，後續研究建議仍須符合[採用前景](回測規則驗證.md#continuation-adoption-prospect)，不以結案自動擴大授權。

<a id="research-version-preflight"></a>
## 研究與測試開始前的版本核對

適用於既有資料診斷、候選回測、遷移及 App 測試。先做與本次任務相關的唯讀核對，再決定是否建置、覆蓋安裝或重算；純文件／既有報告分析不為完成清單而啟動 Simulator、建置或遷移。這是執行程序，不新增研究、採用或發布授權。

### 唯一文件來源

| 查核內容 | 權威文件 |
| --- | --- |
| 目前正式 App／Build、T/S、策略及所用 Baseline | [現行回測規則](現行回測規則.md)；區分最新現況與下方有日期的舊紀錄 |
| 歷次 Baseline、規則 commit、DecisionBase 及報告對應 | [Baseline 歷史](Baseline歷史.md) |
| 變更原因、研究結果、採用／拒絕決策 | [回測規則驗證](回測規則驗證.md) |

不另建一份「最新版本表」。工作交接只作有日期的閱讀路由，每批研究只保存自身來源身分。文件聲稱的狀態仍須由 Git、建置產物、manifest、SQLite metadata 及實際遷移完成狀態核實；衝突時先查明來源，不挑較新數字、不直接改標籤使其一致。發布與本機採用分開，聲稱已發布時另核對對應發布證據；需要確認即時遠端時才查 GitHub，不以本機 HEAD 代替發布檔。

### 啟動前的最小核對

1. **任務與基準。** 寫明本次是唯讀診斷、控制重播、候選或正式遷移，定位核准範圍、樣本、窗口、輸入截止日、本金與加碼設定。確認研究針對現行策略還是某個凍結舊基準；舊基準可作舊策略研究，不自動成為現行策略績效證據。
2. **程式身分。** 核對實際來源目錄、完整 Git commit、未提交差異，以及候選 ID／啟動旗標是否仍有接線。正式規則 commit 與候選來源分開記錄；候選有未提交修改時保留 diff 與相關來源雜湊，不能只記 HEAD。獨立研究工具也記錄工具／引擎來源，不因沒有 App 就省略。需執行 App 時再核對建置組態、bundle ID、App／Build、T/S、策略版本及建置證據；相同 App／Build 不代表相同程式。
3. **資料身分。** 對照 Baseline／DecisionBase manifest 的完整規則 commit、T/S、策略、格式版本與本次輸入設定，核對必要完成標記及 SQLite metadata。需要開啟 store 時另核對 schema、目標股票的 T/S 與 dirty／重播完成狀態；能開啟、欄位有預設值、版本標籤相同都不等於遷移完成。只有原始行情可直接重用，舊衍生值是否可用依本次資料語意決定。
4. **執行環境與輸出。** 需安裝或啟動時，明列裝置 UDID、用途、目前 App 與資料容器及恢復方式，確認無其他任務占用。候選使用隔離環境，不以正常 13 吋／10.86 吋資料承接研究候選或舊版 App；裝置名稱預設值不構成使用授權。輸出使用本批唯一 run ID，查明同名資料與完成標記是否來自舊批次；原 Baseline、DecisionBase、輸入快照及歷史報告不覆寫。

### 不一致時如何處理

| 發現的差異 | 處理方式 |
| --- | --- |
| 已安裝 App 與本次建置不符，或無足夠來源證據 | 在已核准的隔離環境重新建置／覆蓋安裝，保留資料；安裝後重新取得容器並核對可執行檔雜湊與建置產物一致，不只看版號。啟動還須通過下方資料相容檢查 |
| 程式版本相同，但 T/S 語意或 schema 已變 | 依[版本與重算](現行回測規則.md#版本與重算)決定必要版本推進與重播；研究在副本執行。不得只升欄位標籤、改 manifest 或解除 dirty 冒充完成 |
| 較新 App／引擎與舊基準不相容 | 若任務是舊策略，使用已核對的凍結來源；若任務要求現行策略，先指出缺少合格基準。建立新正式 Baseline 仍須相應採用／建立授權，不自動重建 |
| 舊 App 將開啟已遷移的新 store | 禁止啟動；使用版本相容的獨立副本，不對正常資料降版，不刪除 App 來消除不一致 |
| 同名產物、完成標記或候選身分不同 | 保留舊產物，改用獨立批次；不能把上一批 `.complete` 當成本次成功。安全重跑依既有 `--replace-output` 備存規則處理 |
| 只是 App／Build 沒增加，程式與資料契約已確認相符 | 研究測試不為辨識而推進正式版號；以來源、候選 ID 與建置雜湊辨識。正式發布另依[發布流程](發布流程.md)處理 |

版本差異本身不是錯誤，**無法解釋或驗證的差異才阻擋依賴它的執行**。單純覆蓋安裝不等於資料重算；保留容器也不保證啟動後不會遷移。若修復會擴張研究、重建正式基準或影響正常資料，先提出具體影響，其餘可獨立的已核准檢查仍可完成。

### 紀錄、重用與執行後驗證

在本批既有 `protocol.json`、`sources.json` 或研究 README 其中一處保存結論及證據路徑，不為此固定新增一整套文件。至少記錄：預期／實際程式與資料身分、比對結果、需否建置／覆蓋安裝／遷移重播、受保護的原始來源，以及「可執行／阻擋原因」。不適用欄位明示不適用，未知不填成通過。

純診斷可在唯讀核對後執行；需新建置者，先記錄判斷，建置／安裝後補足實際雜湊及容器證據，才啟動重播。候選仍須完成既有零差異控制與第一次分歧前狀態檢查；起始核對不取代結果驗證。完成後以 App／工具實際輸出的 candidate ID、run ID、Sample、基準及版本核對本批紀錄。長時間無可靠進度或出現失敗標記時，依[進度與恢復程序](#execution-progress-recovery)處理。

同一批來源、工具、裝置、資料或設定均未變，可引用已驗證紀錄；任何相關身分變更或其他任務改動環境後，重查受影響項目，不機械重跑全部測試。

以下依 `scripts/run-candidate-backtest.sh` 於 2026/09/17 的實作核對，本次只建立程序，**未新增 runner 自動防護**：

## 執行方式

```bash
scripts/run-candidate-backtest.sh \
  --candidate-id nr2A2 \
  --candidate-flag --candidate-nr2-a2 \
  --sample A \
  --rule-commit 73003cf8f39cbf3a673792957324f508261bd731
```

- `candidate-id` 預期應對應 `DecisionDelta` 使用的穩定 ID；若命名在實作版本中與 `candidate-id` 別名不同（例如 `NR8-S1-C` 實際以 `st02fAdd120` 寫入 DecisionDelta），本腳本會改為以 `decision-summary.json` 的 `candidateID` 與 `sampleID` 對齊完成標記，避免 `candidate-id`/資料夾命名差異造成 timeout。
- `candidate-flag` 是已實作的 Debug 啟動參數。
- `rule-commit` 是正式 Baseline／DecisionBase 的規則 commit，不是未提交候選的工作樹名稱。
- 腳本歷史預設名稱為 `iPad Pro 13-inch (M5)`，不作目前研究裝置指派。必須依[起始核對](#research-version-preflight)確認隔離環境，並以 `--simulator-name` 明確指定；不得把兩台正常資料裝置當作候選環境。
- 同名本機輸出已存在時預設停止；確認是同候選安全重跑後才使用 `--replace-output`，舊輸出會改名保留而不直接刪除。

## 自動完成的工作

1. 確認正式規則 commit 存在，解析指定 Simulator 的 UDID。
2. 啟動 Simulator、建置 Debug App，從建置產物讀取實際 bundle ID。
3. 覆蓋安裝而不刪除 App 資料，安裝後重新取得資料容器。
4. 依 Sample 與完整規則 commit 唯一定位專案端正式 DecisionBase，要求 `.complete`、`.p4b-complete` 與 SQLite 完整，再以暫存目錄同步至目前 App 資料容器；不信任 Simulator 先前殘留副本。
5. 終止舊 PID，再以固定三年、摘要模式及 DecisionDelta 參數啟動唯一核准樣本。
6. 等候與本次 candidate ID／Sample 相符的新 `.complete`；正常運算不以固定短逾時誤判，但 App 若寫出 `.last-run-failure.txt`，或 Simulator 在等待期間不再是 Booted，立即回報實際錯誤或列出最近產物並失敗，不盲等到總逾時。
7. 從 `decision-summary.json` 反查真正的 run ID 與 DecisionBase ID，並核對它就是本次同步的正式基底，不手工猜測輸出路徑。
8. 核對 run ID 確實是 `fixed3y`，並要求 `baseline.json`、`manifest.json`、`periods.csv` 齊全。
9. 搬到 `exports/backtest-candidate-runs/` 與 `exports/backtest-decision-deltas/`。
10. 產生 `run-summary.md`，檢查輸出身分、分數算術、前置狀態、SQLite 完整性、異常值、資金不足與非正常股票狀態。

若建置或回測失敗，腳本保留建置紀錄與最近輸出清單；Simulator 維持開機，方便直接診斷。完成後也保持 Simulator 開機。

內部回測畫面捕捉到錯誤時，會同步把完整的「回測失敗」訊息寫入 App Documents 的 `.last-run-failure.txt`；runner 每次啟動前清除此輪專用舊標記，等待時持續檢查。這可辨識「App 仍在前景但工作已失敗」的狀況，例如候選旗標尚未登錄而被誤判為 Baseline，不必等到總逾時才由畫面人工發現。

若輸出只停在部分 `period-*.store`、沒有 DecisionDelta 完成標記，同時 `simctl` 顯示目標 Simulator 已是 Shutdown，代表回播已失去執行環境，不是仍可等待的慢速階段。保留該次建置 log 與部分產物，重新啟動裝置後重跑同一個已核准候選；專案端若已有同名完整輸出才加 `--replace-output`，只有 Simulator 容器內的未完成目錄不視為可比較結果。

## 判讀界線

S45 採用後，LP06／LP10 歷史研究入口停用；不能用現行正式規則冒充候選。採用前 Swift 來源保存在 `exports/lp10-adoption-source-20260908/`，既有報告不改寫。

歷史 `LP10-HELD-H9-S4` 曾支援 `--full-window-stress`：使用獨立 `9y-fullstress` run ID、T3/S44、策略 `s37-candidate-lp10-held-h9-s4`，對照同 Sample 的 v26 全期間。沿用固定窗口的候選條件，只做 score-only，不建立 DecisionBase／DecisionDelta；每個樣本仍需授權，使用者一次核准 A～E 時可依序完成。九年結果用於路徑及資金風險，不自動取代固定窗口採用權重。

歷史 `LP10-HELD-NONFLAT-H9-S5` 同樣曾支援此入口，使用獨立 S5 `9y-fullstress` run ID、T3/S44、策略 `s37-candidate-lp10-held-nonflat-h9-s5`，對照相同 Sample 的 v26 全期間。S5 固定窗口及計分不變；除了逐日負結餘，也比較買賣／持股變化與期末連續空手交易日數，避免只用期末分數推定沒有停止交易。

全期間摘要除本金不足旗標外，須逐日掃描候選及正式 `browse.store` 的負結餘（低於 -0.01 元，排除浮點尾差），包含持股與空手列，列出股票、最低結餘、日期範圍及筆數。只要任一邊存在負結餘，摘要工具先保存報告，再以退出碼 2 停止 runner 的成功流程；`.complete` 仍表示回測產物完成，不表示資金安全通過。先檢查已保存的報告，不重跑，也不以補錢或修改本金收回語意消除警示。S4-E 鴻準曾因收回加碼本金後負結餘而無法買入，卻沒有設置本金不足旗標，是這項檢查的回歸案例。

歷史 `LP03-FLAT-GT-S2` 曾支援 `--full-window-stress`：另建 `9y-fullstress` run ID，資料 T3/S43、候選策略 `s36-candidate-lp03-flat-gt-s2`，對照同 Sample 的 v25 全期間。只產生 score-only 結果，不建立全期間 DecisionBase／DecisionDelta。

歷史 `LP03-FLAT-GT-S5` 使用相同流程、候選策略 `s36-candidate-lp03-flat-gt-s5` 及 `flat-grade-or-low-entry` run ID，資料與參考為 T3/S43／v25。S5 正式採用後，整個 LP03-FLAT 系列入口停用；本機候選來源保存在 `exports/lp03-adoption-source-20260908/`，既有報告不改寫，不能以 S44 冒充原候選。

`run-summary.md` 只是可靠的第一層摘要，列出正式 Baseline／候選雙方分數、股群、受影響窗口、DecisionDelta 與集中度。它不能自行判定採用、放棄或下一樣本；仍須依 [`doc/現行回測規則.md`](現行回測規則.md)及 [`doc/回測規則驗證.md`](回測規則驗證.md)完成股票窗口、ROI、週期、資金與直接決策分析。

全期間 score-only 壓力測試不產生 DecisionBase／DecisionDelta；App 的結構化產物位於 `Documents/InternalBacktest/Runs/<run-id>/`。`MKT-PP-S02`、RP-S03、SN01-L9-S4 曾支援 `--full-window-stress`，均須依各自歷史程式版本重現，不能用新版正式規則冒充舊候選。此模式禁止控制組及尚未接線的候選，依候選核對 run ID、`T/S`、規則版本及正式全期間參考報告，再檢查 `.complete`、manifest、`browse.store` 與摘要，不讀固定候選的 DecisionDelta。若進度可疑，先檢查同一 run ID 的失敗標記及最近產物，不盲等。

S4 當時的全期間入口使用獨立 `9y-fullstress` run ID，對照同 Sample 的 v23／T3/S41；原固定三年 run ID 與候選條件不變。這段保留為歷史流程，S-N01c 採用後不再啟用。

歷史 `HP04-H9-S4` 的 `--full-window-stress` 使用獨立 `9y-fullstress` run ID、`T3/S42` 及 `s35-candidate-hp04-h9-s4`，對照同 Sample 的正式 v24 全期間。正式納入 H-P04 後也停用此候選入口，僅供依封存程式重現；不產生全期間 DecisionBase／DecisionDelta。
