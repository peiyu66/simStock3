# 舊查詢函數與現行需求對照（2026-10-23）

狀態：本文件保留唯讀盤點及 API 設計；已採納子集的實作與驗收見冷啟動改善計畫第 10 節，未採納 API 不視為全部必做。盤點程式基準 `88ff2bf7e0cc0de7520919e32ca0fe17dbca0221`，App 3.7.6（96）／T4/S65。接續[冷啟動改善計畫](冷啟動查詢與啟動畫面改善計畫-20261023.md)與[日期時間盤點](日期時間使用盤點-20261023.md)。

**有找到封存的舊查詢層，可用來歸納需求，但不宜直接搬回。** 基本的「股票身分＋日期範圍＋來源＋排序＋筆數」足以組成多數每日交易查詢；現行仍缺少明確區分首頁、名錄搜尋、有效窗口、摘要、人工意圖及更新責任的共用介面。現有函數「能查出資料」，不等於「只讀需要的資料」。

索引方面，**目前最有證據的缺口是 Trade 的 `(stock, dateTime)` 複合索引**；Stock 精確代號及 MarketDay 日期已有適用索引。其他組合須由實際 query 成本決定，不能把 group、人工旗標、dirty 等欄位全面加索引。

**2026/10/23 優先順序修訂：**使用者接受首頁共用 Stock Query 取回幾百／千筆基本記錄後再篩股群；它本身不展開 Trade。P1a 的群組 predicate／來源拆分改為低優先、依實測成本決定，取消「DB 必須只返回 18 股」的門檻。先處理 Trade 範圍、limit 與相應索引；下列舊新查詢分類仍完整保留，候選 API 不代表全部必做。日期統一另案執行。

- **保留合理做法：**Q0 容器沒有對應舊查詢 helper；Q1／Q2 對應 R03／R02，可共用完整 Stock 來源。Q4 對應 R05／R10，已有股＋窗口／cutoff／有效價、DESC limit 1；Q7 對應新需求 R12，已有日期 equality／limit 1 與日期唯一索引。Q10 對應 R11，只讀已載入版本／dirty。Q12 對應 R02／R01，到期同步用完整 Stock 名錄、sId 排序與字典配對屬必要，不套群組或 50 筆限制。

## 3．不應帶回的舊語意

1. **精確 ID 與模糊搜尋混用。**A:176 的 ensureStock 透過 substring 搜尋取 first；現行也仍存在。重寫時身分必須用 equality，不把模糊符合當同一股票。
2. **先 limit 再 filter。**A:71–94 及現行 dataModel 220–243 把 limit 套在全名錄 fetch，之後才篩關鍵字；結果不是「符合條件的前 N 筆」。搜尋應先完成等價匹配與排序，再 limit。現行新增搜尋的多詞 AND 也不同於舊 helper 的 OR，不能混改。
3. **可選 Bool 語意不清。**通用 Trade fetch 的 `TWSE=false` 是「非 TWSE」，不等於限定 Yahoo；`userActions=false` 與 nil 都是「不限制」，不是「排除人工操作」。新介面宜用明確 source／action selector，避免呼叫者誤讀。
4. **區間端點模糊。**通用 end 是 `<=`；單日 helper 是 `< 次日日首`；舊 C:317 與現行 uiObject:1248–1260 宣稱 endExclusive，卻傳給含 end 的通用 helper。這是契約不一致，未執行刪除重現。新 API 明寫 throughInclusive／beforeExclusive 或明確 Range，不以減一秒硬湊所有情況。
5. **裸 first／last 不代表目前有效結果。**必須區分原始首末、窗口有效價首末、截止日前末筆、最新正式 TWSE、已完成 T/S 結果。不能只找一筆「舊但有效」來掩蓋最新資料待算；應保留待算遮蔽語意。
6. **關聯先展開再過濾。**舊 viewPage:111 直接對 stock.trades 篩選／排序；現行雖有有界 fetch，窗口安裝與觀察仍會重新展開整關聯。共用 query 若內部又讀 `stock.trades`，就沒有完成縮減工作量。
7. **查詢與寫入混在一起。**ensure、deleteDuplicates、deleteTrades 不是純查詢；舊 B:274 起還包含歷史上清人工標記的重算方式。讀取 API 不應 save／刪除／重設；寫入沿用現行人工意圖驗證、dirty 及事件失效契約，不能搬舊 reset 規則。
8. **舊摘要不等價。**D:283 的 stocksSummary 接 date 卻未使用；舊 C:688 的分母為傳入股票數，現行 uiObject:1698 為有效納入股票數。不是把舊函數換成較快 SQL 就會保持結果，必須以現行[報酬率](報酬率.md)及有效性為準。

## 4．可重寫的共用查詢 API 概念

以下是介面設計，不是已編譯的實作。採少數具用途的入口，共用 predicate／descriptor 組合；不另造一個所有參數皆 nil 的大型萬用 fetch，也不新增持久窗口快照。

| 建議介面 | 輸入 → 輸出 | 查詢形狀／責任 |
| --- | --- | --- |
| `StockQueries.byID`／`byIDs` | 完整代號或集合 → Stock?／[Stock] | equality／集合條件；不強加群組條件；ensure 流程在外層 |
| `StockQueries.grouped`／`inGroup` | 可選的明確群名 → descriptor／[Stock] | 低優先候選：若實測支持，再採全股群非空／單群 equality。現階段允許共用全名錄 Stock Query 後篩群，UI 反應式生命週期保持 |
| `StockQueries.catalogMatches` | 關鍵字、搜尋集合、上限 → [Stock] | 來源拆分時的候選介面，非目前必做：新增搜尋為未入群且上市，多詞 AND、每詞代號或名稱 OR，排序後取 50。保留完整名錄來源與合法同步能力 |
| `TradeQueries.onDay` | stock、台北日期、來源政策 → 當日列／明確決選結果 | stock＋半開日區間；重複與來源優先由當日更新政策處理，不默默刪資料 |
| `TradeQueries.windowEndpoints` | stock、requestStart、cutoff、有效價條件 → firstDate／lastDate／可重用 latest | 首末各最多 1 筆，首頁不拿完整歷史；最小日期欄位與顯示最新列分開，輸入事件使記憶體結果失效 |
| `TradeQueries.rowsInWindow`／`prior` | stock、明確日期上下界、來源／有效價、sort、N → 有界列或價格值 | 明細用窗口；前態用 `date < cutoff`、DESC limit N 後反轉成 ASC。T／S 前態各依其規則需求，不一律縮成 251 |
| `TradeQueries.manualIntentRows`／`manualSummary` | stock、明確修復／重播範圍 → 人工列／存在與筆數 | 原始意圖重驗需列；顯示摘要只需 Bool／Int。正常已確認摘要直接沿用 Stock，修復必須有來源責任，保留未保存編輯語意 |
| `TradeQueries.exists`／`count` | 有限且明確 criteria → Bool／Int | exists 只取能證明存在的最少一筆；count 不為取得整份模型。門檻式數量可以限量判斷，不強求全量 count |
| `MarketQueries.sameDay`／`range`／`prior` | 台北日、日期界線、前態筆數 → MarketDay?／有限資料 | 共用已有日期索引；是否准許前日暫算仍由 SimulationDependencies／更新政策決定 |
| `UpdateQueries.pendingGrouped`／`sourceProof` | 已入群 Stock／來源身分與 cutoff → 待辦或完成證據 | 優先用已載入版本／dirty、收據、ledger，不每次掃 Trade 推測有無變動 |

查詢結果應區分「成功但無資料」與「查詢失敗」；低階 API 保留 throws，不把錯誤一律轉成空集合而讓更新誤判完成。跨股首頁／摘要先重用同輪 endpoint，沒有證據時不引入通用全股歷史快取。

「只回傳 DTO」不保證 SQL 只讀那些欄位。純首末／摘要可評估 [`propertiesToFetch`](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/propertiestofetch)，計數可用 [`ModelContext.fetchCount`](https://developer.apple.com/documentation/swiftdata/modelcontext/fetchcount%28_%3A%29)；實際 SELECT、後續 accessor fault、未保存變更及 SDK 支援仍須在候選實作驗證。需要顯示完整持久結果的最新列，不宜為省幾欄造成反覆 fault。

### 首頁與搜尋來源拆分的適用條件

[viewList.swift:674](../simStock3/viewList.swift#L674) 的 catalogSearchResults 目前與首頁共用 `stocks`。這個 Query 取回的是 Stock 基本模型，可維持現狀；若未來決定加 `group != ""`，才必須先處理來源拆分，否則未入群搜尋資料會一併被排除。

已同步修訂[啟動計畫 P1a](冷啟動查詢與啟動畫面改善計畫-20261023.md#61-p1a-的明確查詢契約與範圍)：來源拆分與群組 predicate 均降為低優先、以實測成本決定，不為只返回 18 股而拆分。若日後採用，須保留多詞匹配、排序後 50 筆上限、選股後成員更新與單一精確名稱／代號「已在股群」提示；不能先截候選 50 再 filter。此處是「縮小共用 Query 時」的正確性條件，不是 Trade 改善的前置工作。精確 ID 與模糊搜尋分開的正確性需求另列 R01，不因 P1a 降級而抹除。

## 5．索引是否足夠：按 query 配對

下表重用既有[query-audit.json](../exports/startup-query-audit-20261023/query-audit.json)，本輪沒有另開資料庫或新增索引。既有庫是被保護的完成副本；對應 SQL 與 RAM 索引實驗不等於擷取到的 SwiftData SQL，也不是正式 App 的實測效能。

| 索引／候選順序 | 現有狀態、可服務 predicate／order／limit | 是否真的缺少／建議 | 成本及必需驗證 |
| --- | --- | --- | --- |
| **Stock `(sId)` unique** | 已有；服務 `sId == id`／指定代號。現行 substring 後篩選沒有善用精確身分 | 不缺索引，缺 R01 精確 query。不要再建同樣欄位的普通索引 | 驗證正確股票與 0／1 筆；多 ID 查詢及模糊搜尋分開，不能靠唯一索引宣稱 contains 是 SEARCH |
| **Trade `(stock)`** | 已有 `ZTRADE_ZSTOCK_INDEX`；可限制單股，仍需逐列看日期／額外條件及排序 | 能避免跨股全表定位，但不足以有效服務常見股＋日期排序；整關聯返回幾千筆仍昂貴 | 保留 SwiftData 管理的既有索引，不手動刪；比較實際返回、掃描與排序成本 |
| **Trade `(stock, dateTime)`** | **尚無，第一優先候選。** 先股 equality，再日期 range／cutoff；可服務首末 ASC／DESC limit 1、單日、窗口、prior N、來源及人工條件的有限候選範圍 | 有明確證據：代表 SQL 原用 stock 索引＋TEMP B-TREE；RAM 候選變成 stock＋date 的 SEARCH，首末／窗口免臨時排序。這是已驗 query plan，不是已驗 App 加速 | 增加每次插入／改日期／刪除的維護成本與空間；量首次建索引、後續冷啟、月下載保存、更新日期及還原。透過 SwiftData schema／#Index 可行性驗證，不能直接 DDL 正式 store |
| **Trade `(stock, dataSource, dateTime)`** | 尚無；適合「指定股＋指定來源 equality＋日期 range／ORDER BY dateTime＋limit」 | **條件式第二候選。** 先量 `(stock,dateTime)` 的來源殘餘過濾；若不構成成本，不加。`source != TWSE` 不等於 equality 情境；未固定 source 時也不能假定這個順序取代通用 stock＋date 排序 | 更寬索引、多一份寫入維護；量來源占比、實際 SEARCH、排序及命中筆數。本輪沒有此候選實測 |
| **Stock `(group, sName)`** | 尚無；group equality 可配排序；全股群 `group != ""` 在既有 RAM 計畫仍是 index SCAN，只少臨時排序 | **低優先、非必加。** 已量 Stock fetch 約 0.075 秒，沒有證據應優先加索引或拆分 Query；可維持全名錄後篩群，不要求先只返回 18 個模型 | 量真正 SQL、排序成本及改名／換群維護成本；不能把 SCAN 描述成只搜尋 18 列，也不據此新增 group schema |
| **MarketDay `(dateTime)` unique** | 已有；同日 equality 已是 SEARCH，日期範圍與日期順序可利用現有索引 | 現階段足夠，先把 fetchAll 改成所需 range。全表循索引 SCAN 仍會讀全部，不能靠另一個日期索引改善 | 驗證現行 SQL 有日期上下界、實際返回／fault 量及所需前態完整；不新增重複索引 |
| **人工標記、正價、dirty、版本、isListed 等額外索引** | 現有未見此類自訂索引。多為 OR、低選擇性或股群內少量 Stock 欄位；正價通常也是大多數資料 | 暫無增設依據。人工摘要先修復責任／去排序／count 或 exists；dirty／版本已可看已載入 18 股；搜尋先明確範圍及語意 | 寬 covering 或多旗標索引增加儲存／寫入，仍可能有殘餘條件。只有實際 profile 顯示瓶頸才另提，不預先設計一整排索引 |

索引欄位順序要對應實際條件：先定位股票，再按日期範圍與順序取最少資料；有指定來源的情境才評估把來源放在日期前。這符合 SQLite 的多欄索引及查詢／排序規劃原則，但是否採用仍由本案生成 SQL 與計畫確認。[SQLite Query Planning](https://www.sqlite.org/queryplanner.html)

## 6．可執行的改善順序與驗收

1. **P1b/P1c：優先有界 Trade。**首末／最新用 limit，窗口／prior N 明確給日期界線；共用有效價條件與事件失效，移除 `stock.trades` 觀察旁路。保存窗口外原始資料不等於啟動讀取；未入群股票不展開歷史。日界線沿用獨立日期統一任務的共用契約與驗證，不把日期產品修改混入本文件任務。
2. **P2：實際 query＋索引驗收。**依完成分類後的 predicate／排序／limit，優先驗 `(stock,dateTime)`；其他索引只按殘餘成本追加。每個入口記投影、生成 SQL、EXPLAIN、返回／materialization／fault、主執行緒耗時；schema 首次成本與每次冷啟分開。P1a 不是相依前置。
3. **P3/P4：摘要／來源／大盤。**exists/count 與人工意圖列分開；已確認來源結果重用；大盤有界載入。舊例外不成為啟動掃描藉口；不得把未知／失敗當完成。
4. **P1a：低優先、成本支持才做。**首頁／搜尋來源拆分、`fetchGrouped` 的群組 predicate 及 Stock 群組索引個別評估，不捆成必做。可保留 Q1/Q2 全名錄 Stock 後篩群，不以返回 18 作門檻；完整名錄搜尋、排序與反應式成員變化必須保留。R01 精確 ID 查詢另按身分正確性評估，不與這項效能優先級混淆。

正確性驗收採目前規則，保留同日來源替代、窗口首末、閏日／截止日、N 筆不跨下界、人工有效意圖、T/S dirty／版本、缺市場及無變動回前景。股票 ID 搜尋需驗精確／部分、多詞、未入群、已入群與 50 筆界線；排序相同日期的決選行為另須釐清，不能在「優化」時任意新增不同結果。

**完成界線：**本輪建立查詢對照與唯讀證據，並依使用者決定同步修訂兩份文件的優先順序；沒有產品修改、schema 修改、資料修復、正式庫／實機操作或 Git／發布。以上 API 尚未編譯，新增索引尚未做 SwiftData 遷移與實際 SQL 驗收；有依據的下一個實作範圍為 P1b/P1c 的 Trade 查詢，再接 P2，P1a 可保留現狀。日期統一另案執行，查詢改善仍待實作授權。
