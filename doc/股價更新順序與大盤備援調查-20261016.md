## 已查證：續跑與日期

- 成功月份的行情與最早 dirty 起點會保存。每次手動重試重新規劃，不使用「Yahoo 全輪完成」作為 TWSE 成功條件。個股最新正式 `TWSE` 日期已達截止日且歷史起點足夠時，通常不重抓；Yahoo 列不算正式覆蓋。
- 同輪續批有各股票／大盤的下一月份游標，避免重抓已成功的前進月份；游標只存在記憶體。取消或重啟後，以資料庫首尾重建範圍，最新邊界月份可能再查，並不是完整的持久月份帳本。來源空回應、停牌、內部缺日與儲存錯誤不能單靠月份首尾保證完整。
- 日期統一 Asia/Taipei。一般交易日 09:00–13:30 請求 Yahoo；13:30 後按股票保存一次成功收盤補查，正式今日已有 TWSE 就略過。15:35 才把「今日」列為應有正式收盤的截止日，此前為前一交易日；週末／日曆休市向前找交易日。15:35 是程式政策，不是來源必然到齊的保證。
- 日曆有效快取、跨年及失敗節流各有處理；日曆未知時截止日為 nil，現行正式市場閘門仍阻擋。臨時停市未及時反映於日曆時，可能一直期待不存在的當日資料，不能因查不到就自行宣告休市。
- Yahoo 大盤驗證同日、行情時間及 OHLC，保留 `quoteTime`；個股現行 writer 只排除過度未來時間，沒有相同的同日與舊快照退回防護。舊日回應仍可能被算為成功；收盤完成記號用接收時間，不能據此保證行情時間已過收盤。調整流程時需一起補上來源時間驗證。

## 獨立問題：TWSE 已完、Yahoo 未完後的同目標重試

使用者另明確回報：「TWSE 已經補完，但是 Yahoo 未補完，所以重來時又重複 TWSE 的查詢。」此問題與大盤順序分開處理。

**已查證：目前主入口未找到「Yahoo 未完成 → TWSE 完成記號失效」的直接連線。** 清單及單股更新都呼叫 `startDailyPriceUpdate → updateDailyPrices`，每次先呼叫 TWSE 規劃，但是否請求個股月份看 `needsForwardUpdate` 的已存 `TWSE` 日期及歷史範圍；正式大盤也以已存正式日期判定。這兩個判斷不讀 `timeTradesUpdated`、`timeYahooCloseRefreshed` 或診斷的 `completedAt`。

`timeTradesUpdated` 確實存在「舊管線 allGroup 全部返回後才寫」的程式，但屬 `downloadTrades/performRunRequest`；不可套成目前畫面更新按鈕的根因。現行 `completedAt` 是整輪返回才保存的診斷時間，即使部分失敗也會記錄，並非 TWSE 完整性 checkpoint。

**已查證的續接缺口：** 個股 Yahoo 每檔成功行情立即保存，但 `successfulStockIDs` 是該輪記憶體集合；13:30 後的 `recordYahooCloseRefresh` 要等整輪 Yahoo 返回才保存。若在後面某檔等待時關閉／中斷，先前股票可能已存好行情，卻未留下逐檔收盤完成記號，下次會再查 Yahoo；盤中本來就不使用這個收盤記號。TWSE 的下一月份游標也只在同輪記憶體保存。這些缺口支持做來源獨立續接，但不證明會導致所有已齊 TWSE 重送。

| 下次看到的情況 | 能判定什麼 |
| --- | --- |
| 「準備更新」「檢查本機股價完整性」 | 只證明重走入口／本機檢查，不能算 HTTP 重送 |
| 「正在確認交易日曆」 | 可能是日曆請求或加入進行中請求，不是個股 TWSE 月份下載 |
| 「股票代碼…補齊近期／歷史股價 YYYY/MM」 | 文字在 `requestMonth` 實際呼叫處，代表已嘗試該月份請求 |
| 「大盤 補齊歷史指數 YYYY/MM」 | 指數來源請求，不能當成個股歷史重抓 |

若真有相同個股／月份重送，候選原因為日曆失效使 cutoff=nil、跨 15:35／交易日而截止更新、上游成功但沒有應有截止日、邊界月份／歷史起點不足、新股／變更範圍、保存未成功，或裝置版本不是本次程式。均屬待今日診斷驗證的假設，不把使用者的觀察否定為只是 UI。

**最小 checkpoint 提案：** 沿用資料列作正式證據，新增有界的更新工作身分與逐項狀態：`來源 × 對象（個股或市場）× 台北目標交易日／正式 cutoff × 月份或 Yahoo 更新輪次`，分開記「輸入已保存」「衍生結果待重算／已完成」「失敗待重試」。每檔／每月成功且保存完成即寫入，不能等另一來源或整輪完成；重試同一工作只補剩餘項目。Yahoo 盤中必須含輪次／新鮮度，不能因今天曾成功就整日略過。

重試仍先做輕量失效檢查：台北換日、跨正式公布 cutoff、日曆版本／內容改變、股群新增移除、歷史起點／模擬設定改變、T/S／市場版本、dirty／資料修訂、刪除／還原及時鐘倒退；只重規劃受影響項目。歷史原始價成功可沿用，不因 S 重播而重抓。不要僅以全局 lastUpdated 或股票清單 hash 丟棄所有進度。現行來源相同月份可能修正，checkpoint 也不能永遠禁止正式再驗。

## 提案：備援邊界及必要防護

1. **只在運算讀值層備援。** 優先同日正式值，其次同日有效 Yahoo 快照，最後才是上一交易日正式且技術版本完整的市場狀態。保留 `decisionDate`、`sourceDate`、`quoteTime`、來源／資料修訂及暫用原因；顯示「暫用 YYYY/MM/DD 大盤」，不顯示成今日實測指數。已有同日快照後本輪查詢失敗，不退回更舊日期。
2. **不建立假今日列。** 不把昨收填今日四價、不增加市場觀察筆數、不推進九日／KD／OSC／路徑天數，也不把缺資料標記成正式補齊。冷啟動仍須辨識哪些當日模擬依賴暫用值；持久暫算若沒有來源／待刷新身分，就不能當正式結果。
3. **限制可降級範圍。** 先確認前一交易日以前所需正式歷史和 T/S／市場版本完整。首次無 cache、舊版遷移、缺多個市場交易日、來源日期無法驗證時，不任意使用很久前的值計算完整模擬；個股報價可另行顯示暫存，模擬保留待完成。週末連假不等於缺多個交易日，按市場日曆計算落後程度。
4. **明訂差分語意。** 直接讓所有 `observation(on:)` 自動 fallback 會污染歷史查詢，也可能使 S-E01 的兩端落到同一市場日，OSC 差變 0；個股停牌時兩端亦不一定相鄰市場日。建議以完整快照凍結作為明示的盤中假設；日期配對不成立的差分條件標為不可用，不偽造零差。這會改變暫算訊號，需使用者確認及測例，不能宣稱等價。
5. **補到後重新計算。** Yahoo 真值到達：刷新所有有同日個股行情的股票、Grade、警戒與 P10，即使價格沒變或該股本輪查詢失敗。TWSE 修正／補回較早日：沿最早 dirty 起點重建市場再重播下游。只有昨日個股行情者不可套今日大盤。已有相應函式及測例，但目前 Yahoo 大盤先保存、再逐股刷新，沒有與正式大盤相同的持久 dirty 傳播；中途關閉可能留下舊結果，後置設計需補可恢復的修訂／待重算記號。
6. **暫算保護人工意圖。** 現行 `simUpdate` 會清除冗餘／無效反轉、加碼。暫用市場跑一次後若刪掉意圖，正式市場稍後到達也無法憑空恢復。暫算及 P10 應使用同一份不可變人工意圖副本，不因備援結果永久清除；正式重播再依既定規則驗證。
7. **避免時間錯配及前視。** 個股與大盤分開下載本來就不同步，後置後新大盤可能晚於個股行情；顯示雙方時間並以固定快照計算。若決策時間定義為個股 quoteTime，不能讀其後才取得的市場資料；若定義為整輪完成時，須明示個股可能較舊。歷史回測仍用同日正式收盤；不得把事後最終大盤帶回早盤決策，也不能用現有收盤 Baseline 證明此盤中備援有效。盤中重現需當時快照／可取得時間。

以上為程式風險推導，未以今日裝置資料重現。尤其「個股已更新到前一日，但正式大盤缺了前一日」涉及前日模擬前態不可靠，不能當成只有今日指數缺值。

## 初次調查提出的調整計畫（後續已批准，實作界線見後段）

1. **先分離更新責任及同目標續接。** 實作上節逐來源／對象 checkpoint，保留個股成功資料與完整性檢查；Yahoo 個股先取、當日大盤最後取。TWSE 大盤網路失敗不阻擋個股報價取得；但正式歷史重播仍須等依賴完整。若需在歷史 dirty 時先顯示行情，須拆開現行 Yahoo writer 的「收報價即重算」，避免直接修改並使用未完成前態。只搬一個函式不足。
2. **加有限的當日 resolver 與暫算狀態。** 限已完成歷史的今日情境，採上節日期／版本／差分政策；正式歷史 lookup 維持 exact-day。同步補個股日期驗證、來源分段完成／失敗與診斷。正式個股完成檢查也需直接驗證截止日；現行 `stockInputsReady` 主要靠請求成功及剩餘月份，不能把 HTTP 成功等同截止日已到齊。
3. **最後大盤刷新並原子化收尾。** 行情改變持久標記受影響範圍；同日重算及 P10 使用一致快照，保護人工意圖。失敗維持個股報價與暫用提示，下一輪只補未完成來源；取消／重啟可恢復，不重抓所有已完成歷史。
4. **先做隔離 mock 與重播對照。** 完成下表才評估版本及正式採用。若改持久 S 語意，依專案版本契約另處理；本次不預先宣告「不用升 S」或建立新 Baseline。單純換序可比較正常來源下結果零差異；備援分支須獨立驗證，不能用零差異掩飾預期差別。
