# 回測決策旁錄與差異資料設計

## 文件狀態與目的

本文件是「標準化決策旁錄」的設計與實作紀錄。P1～P4 已完成；P3G-1 另把上游 `GRADE` 決策事件加入 Sample A v2 DecisionBase，使 Grade 規則候選也能從第一次直接分歧開始比較，Sample B 仍維持 v1、待真正需要跨樣本 Grade 檢驗時再重建。候選只保存相對差異、第一次分歧、重新一致、期末結果與可直接閱讀的標準分析；P5a 已完成單一賣出事件的行動級反事實，P5b 已完成 ADD 階段 A-P08 非零票的單票移除反事實；其他規則須在具體事件核准後接入同一介面，加票／改票及 P6 也仍待核准。這套研究旁錄不改變現行 [Baseline 與正式規則](現行回測規則.md)。

標準化旁錄要回答：候選相對 Baseline 的差異起於哪一條規則、哪一種交易決策、交易當時哪個 Grade、哪個固定窗口與哪檔股票，以及後續 ROI、持股週期、輪次、資金與回測績效分數如何改變。它也作為規則貢獻圖、臨界值掃描、邊界事件反事實重播與簡單規則生成器的共同輸入。

本設計不把研究資料寫入使用者的正式 SwiftData 資料庫，不讓旁錄影響 `tUpdate`／`simUpdate` 結果，也不以模型自動採用或發布交易規則。候選生成後仍遵循[回測規則驗證](回測規則驗證.md)的單一假設、獨立副本、Sample A／B、固定窗口與完整模擬流程。

## 核心決定

1. 行情與 `t`／`v` 技術值只保存在現有技術資料基底，不為 Baseline 或候選重複保存。
2. 每個正式 Baseline、Sample、窗口設定與資金設定建立一份「決策基底」；候選不複製決策基底，只記相對差異。
3. 規則票數採稀疏格式，只保存非零貢獻；固定為零的規則不產生資料列。
4. 候選完成受控回測後，以相同事件鍵和 Baseline 比較；狀態、票數與行動都相同時不寫入，也不建立第二份完整 DecisionBase。
5. 正式長期證據與可重建快取分開。完整事件基底及大量反事實分支可以清除重建，候選設定、manifest、第一次分歧、差異摘要與採用判讀才長期保留。
6. 動態 Grade 必須在當日模擬結果更新累積值之前擷取；完成模擬後不得由同一 Trade 列倒推。
7. 交易決策分數與回測績效分數分欄、分名保存，不以含糊的 `score` 同時表示兩者。

## 現況與容量基準

2026/08/11 的 S11 固定窗口正式報告中，Sample A `browse.store` 約 21 MB，Sample B 約 22 MB；四份固定窗口／全期間 A／B 正式報告合計約 87 MB，其他 JSON、CSV 與 HTML 只占極小部分。若每個候選都另存完整 `browse.store` 或寬表技術快照，每日十個候選即可增加約 200～400 MB，因此明確禁止「一個候選一份完整每日資料庫」的設計。

第一版容量目標不是先訂死檔案大小，而是保證以下結構性條件：

- 候選新增的行情與技術值資料量必須為零。
- 候選新增的 Baseline 相同事件資料量必須為零。
- 未觸發規則不得留下零值資料列。
- 零差異候選只保留設定、品質檢查與零差異摘要。
- manifest 必須記錄事件數、差異事件數、第一次分歧數、檔案大小與相對 Baseline 的差異率；差異率異常擴大時先檢查規則作用與紀錄器，而不是截斷證據。

原型完成後才以實測決定容量警示線；初步期望完整決策基底為數 MB 等級，一般候選 delta 為數十 KB 至數百 KB，路徑廣泛改變的候選可以到數 MB。

## 識別鍵與去重邊界

### 輸入快照 ID

`inputSnapshotID` 至少由 Sample、股票清單與股群、行情截止日、T/S 資料規則版本、技術基底檔案雜湊形成。相同 ID 表示行情與技術值可共用；任一項不同就不得誤用舊資料。

### 決策基底 ID

`decisionBaseID` 由 `inputSnapshotID`、策略規則版本、精確規則 commit、固定／全期間窗口、窗口起訖、本金、加碼、交易成本與其他固定成交假設形成。不同 Sample 或不同窗口起點會產生不同動態 Grade 與持倉路徑，因此不能只依策略版本共用決策狀態。

### 事件鍵

`eventKey` 由 `decisionBaseID + windowID + stockID + tradeDate + decisionPhase + sequence` 構成；`decisionPhase` 明寫 `GRADE`、`H_BUY`、`L_BUY`、`SELL`、`ADD`，避免上游評等與 H／L 股群、H買／L買混淆。`sequence` 預留同日同階段將來可能有多次評估時使用。

### 狀態指紋

`stateFingerprint` 對決策前真正影響後續的模擬狀態產生穩定雜湊，包括動態 Grade、庫存、成本、資金餘額、持股日數、累積 ROI／週期／輪次、原買入型態與加碼狀態；不重複納入可由 `inputSnapshotID + stockID + tradeDate` 取得的行情及技術值。`GRADE` phase 是例外：Grade 是該事件的輸出，不得又放進其前置指紋，因此只雜湊產生 Grade 的原始模擬狀態；後續 H／L／S／A phase 仍把已決定的 Grade 納入指紋。

候選和 Baseline 的事件鍵、狀態指紋、非零票集合、門檻與行動完全相同時，不寫 candidate delta。候選路徑若之後重新一致，也從重新一致處停止保存差異。

## 標準化紀錄

### 規則目錄 `rule-catalog.json`

每個決策基底保存一次：

| 欄位 | 用途 |
|---|---|
| `catalogVersion` | 規則目錄格式版本 |
| `ruleID` | 穩定正式規則代號，如 `H-P01`、`S-T01c` |
| `decisionPhase` | H買／L買／S賣出／A加碼 |
| `polarity` | 正分、負分、門檻或資格 |
| `valueType` | 整數、小數、布林、Grade 映射或 ROI 門檻 |
| `description` | 簡短現象目的，不保存當期分數結果 |

規則的精確條件仍以規則 commit 與[現行回測規則](現行回測規則.md#現行完整規則登錄)為準；目錄只提供機器可讀的穩定 ID 與顯示文字。

### Baseline 決策事件 `decisions.sqlite`

每次進入一個實際會評估的決策階段時記錄一筆 `decision_event`：

| 欄位群 | 保存內容 |
|---|---|
| 身分 | eventKey、windowID、stockID、date、decisionPhase |
| 決策前狀態 | decision-time Grade、持倉、成本、ROI、持股日數、輪次、資金與 stateFingerprint |
| 資格 | 是否具有首次買入、賣出或加碼資格；不成立時使用穩定 reason code |
| 分數 | `decisionScore`、`decisionThreshold`、距門檻差值；H／L／S／A 分欄語意 |
| 行動 | 預定規則、實際成交行動、買入型態、加碼與資金不足狀態 |
| 品質 | 有限值檢查、資料來源、是否準備期、紀錄器格式版本 |

每條非零票另寫入稀疏 `event_vote(eventKey, ruleID, contribution)`；不得為每條未觸發規則寫 `0`。Grade 路由、ROI 資格或門檻若沒有直接加減分，仍以 `valueType` 與實際門檻值保存，不能假裝成一票。

原始價格與所有 `t`／`v` 欄位不寫入決策資料庫；分析器依 `inputSnapshotID + stockID + date` 從 `TechnicalBases` 讀取。只有研究結果需長期自足、且該技術值是第一次分歧的直接條件時，才把少量相關值複製進 `first-divergence.csv` 供人工閱讀。

### 候選差異 `decision-delta.sqlite`

候選只保存：

- 候選相對 Baseline 改動的規則、門檻或 Grade 映射。
- 非零票集合、分數、門檻、資格、行動或 stateFingerprint 至少一項不同的事件。
- 每檔股票、每個窗口的第一次分歧。
- 分歧後新增、消失或改變的成交事件。
- 路徑重新一致的位置。
- 期末 ROI、平均週期、輪次、Grade、資金不足與回測績效分數 delta。

每筆 delta 使用 `changedFields` 位元集合，只有變更欄位才有值；不重複保存 Baseline 欄位。候選產生 Baseline 不存在的事件時，使用完整候選事件並將 `baselineEventKey` 留空；Baseline 事件在候選消失時保存刪除標記。

### 人工可讀摘要

每個候選固定產生小型檔案：

- `decision-summary.json`：事件總數、觸發數、決定性事件、差異事件、第一次分歧、重新一致與品質檢查。
- `distribution.csv`：依 Sample × 窗口 × 股票 × decision-time Grade × 決策類型 × 規則代號彙總評估、觸發、決定與差異次數。
- `first-divergence.csv`：每個股票窗口第一次不同決策的日期、Grade、規則票、門檻、行動與期末結果 delta。

上述摘要可以回答差異集中在哪個 Grade、窗口及個股；但「某個 Grade 貢獻多少最終績效分數」不能只用事件次數相加，仍須區分第一次分歧與後續路徑連鎖。

## 產生頻率與保留週期

| 資料 | 產生時機 | 用途 | 預設保留 |
|---|---|---|---|
| TechnicalBase | Sample、T 版本或行情截止日改變時 | 共用行情與技術值 | 保留目前與仍被正式 Baseline 引用的版本 |
| DecisionBase | 正式 Baseline、Sample、窗口、資金／加碼或固定成交假設改變時 | 規則貢獻、臨界值與候選比較基準 | 保留目前正式版；舊版若有正式報告引用則匯出一次 |
| Candidate delta | 每個受控候選完整回測時 | 差異歸因與候選摘要 | 檢驗批次結束前保留；結案後依下述規則縮減 |
| 零差異摘要 | 每個零差異候選 | 證明已跑且品質正常 | 長期保留小型摘要，不保留空 delta DB |
| Counterfactual | 只有異常、因果不清或已核准生成研究時 | 單一邊界事件的邊際效果 | 預設是可重建快取；只保留影響決策的摘要與少量代表分支 |
| 分布與第一次分歧 | 每個候選完成時 | Grade／窗口／個股來源分析 | 隨候選證據長期保留 |
| 正式 HTML／Baseline | 正式採用、階段完成或使用者要求時 | 人工判讀與發布依據 | 依既有回測紀錄約定保留 |

檢驗批次結束後：正式採用候選、絕對變化超過 1 分的高訊號候選、資料異常案例及使用者指定候選保留完整 delta；一般已拒絕候選只保留 manifest、設定、`periods.csv`、摘要與第一次分歧。被清除的檔案必須能由 `inputSnapshotID`、`decisionBaseID`、規則 commit 與候選設定重建。

## 差異歸因的語意

1. **直接分布**：精確統計候選與 Baseline 哪些決策事件不同，以及事件當時的 Grade、窗口、股票和規則票。
2. **起源歸因**：把每個股票窗口的後續路徑差異連回第一次不同決策；這回答「差異從哪裡開始」，不宣稱第一次事件獨占全部期末分數。
3. **期末結果**：以現有 `periods.csv` 精確核對股票窗口的 ROI、週期、輪次、Grade 與績效分數差異。
4. **因果邊際效果**：只有固定同一事件前狀態、改變一票或一個行動後向前重播，才可稱為該事件的反事實邊際效果。

Baseline 與候選第一次分歧之前應具有相同 stateFingerprint；若不同，表示輸入、窗口、重算或紀錄器不受控，該次結果停止使用。第一次分歧後兩條路徑的 Grade 可以不同，不能把同日期不同 Grade 強行視為同一情境。

## 回測程序

### 階段一：讀取式旁錄

1. 將目前 H-N09、L-C02、A-N01 的候選專用 recorder 一般化為統一決策 recorder。
2. 以 DEBUG／內部回測模式啟用，正式 App 預設不寫旁錄。
3. 用同一 Baseline 分別開啟與關閉旁錄，核對 `baseline.json`、`periods.csv` 與核心模擬列位元級一致。
4. 檢查 decision-time Grade、H 先於 L、持倉資格、準備期排除及模擬截止日裁切。

### 階段二：規則貢獻圖與臨界值掃描

1. 從 DecisionBase 統計規則評估、觸發、決定性與獨有決定次數。
2. 建立規則重疊矩陣，但不把同一決策事件共現、Jaccard 或單向涵蓋率直接解讀為重複規則。
3. 先對 DecisionBase 已保存的 H買／L買最終分數門檻，列出上下最近的實際分數與局部受影響事件。逐條技術條件只有在旁錄另存原始觀察值後，才能形成內部參數的相鄰臨界值；不得由規則描述猜值。任何候選仍依既有約定一次只移動一個門檻並完整回測。

### 階段三：候選 delta

1. 候選仍獨立完整跑每個窗口，完成後以穩定事件鍵讀取並比較對應 Baseline event。
2. 只寫差異、第一次分歧、重新一致與期末 delta。
3. 以既有已知零差異候選驗證輸出只有零差異摘要；以已知廣泛差異候選驗證 Grade、窗口、個股與 `periods.csv` 可核對。
4. Candidate delta 不取代候選獨立 store 與完整 `simUpdate`；它只縮減分析證據的重複保存。

### 階段四：限定反事實與簡單規則生成

1. 先由貢獻圖與臨界值縮小到真正接近門檻的事件，不對全部每日資料逐一重播。
2. 以指定 eventKey 強制增加／移除一票或改變一次行動，從窗口起點完整向前重播。
3. 以 ROI、持股週期、資金占用與後續路徑 delta 建立反事實結果。
4. 規則生成器只允許一個技術條件，或 Grade 加一個技術條件；最多兩個條件、足夠觸發、非單股／單一窗口主導，並輸出小幅固定投票候選。
5. 每次最多挑少量候選進入現有逐項檢驗；採用一條後以新 Baseline 重建 DecisionBase，不一次採用一包生成規則。

## 驗證與停止條件

實作每一階段都必須先通過：

- 旁錄開關不改變任何正式模擬結果。
- `decision_event` 的股票、日期、窗口和總數可重現。
- 決策票加總、門檻、資格與最後行動一致；不允許不明 mismatch。
- Grade 取自決策更新前，期末 Grade 只用於期末摘要。
- 候選 delta 的股票窗口結果與 `periods.csv` 一致。
- 0、Inf、NaN、截止日外行情或準備期誤納時立即停止。
- delta 意外接近完整事件量時，先判斷是候選廣泛改變路徑或比較鍵錯誤；不得為節省容量截斷資料後繼續判讀。

第一階段若無法穩定取得 decision-time Grade、逐條票數或與原 Baseline 位元級一致，停止後續臨界值、反事實與規則生成，不以完成後倒推資料替代。

## 實作段落與交付

1. **P1：格式原型**：定義 ID、SQLite schema、JSON／CSV 摘要與容量量測程式；使用一個 Sample A 固定窗口副本驗證，不改正式規則。
2. **P2：Baseline DecisionBase**：一般化 recorder，完成 H／L／S／A 四階段與位元級無副作用驗證；P3G-1 再以 v2 schema 補上上游 GRADE phase。
3. **P3：Candidate delta**：完成差異比較、第一次分歧、重新一致、分布與期末核對；以零差異控制及兩個不同影響幅度的歷史候選驗證。
4. **P4：分析器**：P4a 已交付規則貢獻、Grade × 窗口 × 個股、第一次分歧、直接規則差異與路徑連鎖摘要；P4b 已交付規則重疊矩陣、共現方向及 H買／L買相鄰決策分數清單。逐條技術參數須待原始觀察值旁錄後才能可靠產生，不納入本階段猜測。
5. **P5：限定反事實**：P5a 已完成單一 S 賣出事件的 `HOLD → SELL`；P5b 已完成 ADD 階段 A-P08 非零票的單票移除，介面可供其他規則在核准後接入。兩者都先做零變更控制、精確核對事件鍵與 state fingerprint，再產生效用摘要；其他規則或加票／改票仍只在具體事件核准後擴充。
6. **P6：簡單規則生成研究**：在既有規則檢驗完成後才啟動，先定義候選模板、資料切分、多候選防過度擬合與停止條件。

P1～P4 是標準化旁錄的核心；P5～P6 是依研究價值另行核准的後續功能。每個段落都要能獨立驗證、交付或停止，不把整套研究工具一次併入正式 App。

## 特別說明

- 標準化旁錄的第一目的不是保存更多資料，而是只保存「決策所需的共同基底」及「候選真正改變的部分」。
- `browse.store` 是瀏覽完整模擬結果的副本，DecisionBase 是決策分析索引；兩者用途不同。正式 Baseline 仍可保留一份 `browse.store`，候選不因需要 delta 就都保留完整瀏覽副本。
- 壓縮不能取代去重。先消除技術值、零票與 Baseline 相同事件的重複，再考慮 SQLite 頁面、整數枚舉或檔案壓縮。
- 決策旁錄只能提高歷史差異的可解釋性與研究效率，不能增加不存在的歷史資料，也不能把同一 Sample 反覆搜尋後重新變成未見驗證資料。
