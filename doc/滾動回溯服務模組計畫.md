# 滾動回溯服務模組計畫

## 文件狀態

- 方向已確認：建立統一的滾動回溯服務模組，先由 `simUpdate` 的既有回溯需求試用，再分段處理 `tUpdate`。
- 本文件只規劃架構、任務順序與驗收條件；建立本文件本身不代表已授權任一程式修改、資料版本推進、完整重播、commit 或 push。
- 每個任務仍依 `AGENTS.md` 的核准與停止條件個別執行，不因列入本文件而自動接續。

## 目的

目前 `tUpdate` 與 `simUpdate` 已先把單一股票的 Trade 依日期載入記憶體，但部分逐日計算仍會反覆掃描相同歷史區段。這些回溯不是資料庫每筆查詢，主要成本是對記憶體陣列重複做窗口統計或尋找前次事件。

本計畫建立共同的 `ReplayRollingContext`，讓技術值與模擬規則事前登記需要的窗口或事件摘要。完整重播由已知初態開始；局部重算、Yahoo 當日與 P10 則只在起點取得一次必要前態，其後依日期順序更新，不讓每一筆 Trade 重複搜尋同一段歷史。

預期改善包括：

- 減少 `simUpdate` 對最近加碼及惡化趨勢界線的逐日回掃。
- 統一既有 G-M02 認賠降級狀態的初始化、更新與 P10 分叉方式。
- 分段降低 `tUpdate` 對 9／20／60／125／250 筆窗口的重複掃描。
- 讓完整重播、局部重算、Yahoo 當日與 P10 使用相同前態語意。
- 保持 Context 為單次運行狀態，不因效能改造任意新增 SwiftData 欄位。

## 非目標

- 不修改任何 H／L／S／A／G 規則條件、分數或門檻。
- 不把候選研究狀態放入通用 Context；正式欄位仍須經具體規則檢驗與採用。
- 不以一個可任意塞值的字典取代具名、可型別檢查的領域狀態。
- 不把一次性的遷移檢查、重算起點定位或畫面查詢納入逐日滾動服務。
- 不為了宣稱完成而一次重寫全部技術指標；每批只改一種可獨立驗證的回溯機制。

## 現況盤點

### 已經是滾動計算

- G-M02：完整或局部重播在起點找出一次 `gradeLossCutPenaltyLevel`，之後依每日自動完整賣出結果更新。
- Grade 適配趨勢：Fast／Slow EMA、觀察筆數、分段及區段極值都以前一筆 Trade 保存值更新。
- 模擬庫存、成本、輪次、累計 ROI 與持股日數都以前一筆模擬狀態承接。
- KD、OSC EMA 等遞迴技術值已使用前一日狀態，不需要一般窗口服務。

### `simUpdate` 仍會回溯

| 回溯需求 | 現行方式 | 適合的 Context 摘要 |
|---|---|---|
| G-M02 起始狀態 | 從重算起點往前找最近一次非人工完整賣出 | `gradeLossCutPenaltyLevel`；只在起點初始化一次，賣出後更新 |
| A-E01／S-T02 最近加碼 | 每個持股日反向掃描最多 60 筆，同時計算 38／45／60 日條件 | `tradingDaysSinceLastInvestment`；加碼後歸零，逐交易日遞增，新持股輪次重設 |
| L-P10 脫離惡化後恢復票 | 每日向前找最近一次惡化預警或惡化確認 | `lastWorseningBoundary`；遇預警或確認時更新，其餘日期沿用 |

### `tUpdate` 仍會回溯

| 回溯需求 | 現行方式 | 適合的 Context 摘要 |
|---|---|---|
| 收盤價 MA20／MA60 | 每日重加 20／60 筆 | 固定長度窗口與合計 |
| 九日技術／價格極值 | 每日重掃九筆 | 單調佇列或小型固定窗口 |
| 125／250 日價格高低點 | 每日分別重掃窗口 | 高低價單調佇列 |
| 125／250 日各項 Z 分數 | 每個指標每日各掃兩次計算平均與變異 | 窗口、合計與平方合計；須處理浮點運算順序 |
| 合格成交量序列 | 每日先倒找最近 250 筆正式 TWSE 日，再重算多組窗口 | 只在合格 TWSE 日推進的專用環形窗口 |
| MA 趨勢短暫反轉補看 | 直接定位約五筆前的狀態 | 範圍固定且很小，暫不改造 |

P10 對同一天最多試算十個價格，最後再以正式價格恢復一次；現行每個情境都會重新執行上述 `tUpdate` 回溯。這是技術 Context 完成後應特別利用的分叉情境。

## 模組設計

### 頂層生命週期

```swift
struct ReplayRollingContext {
    var technical: TechnicalRollingContext
    var simulation: SimulationRollingContext
}
```

`ReplayRollingContext` 統一負責：

- 從重算起點以前的必要歷史建立前態。
- 依交易日順序提供當日計算所需摘要。
- 在當日技術值與模擬行動確定後提交狀態。
- 為 Yahoo 與 P10 從同一份正式前態建立互不污染的副本。
- 限定 Context 只屬於單一股票、回測窗口及試算情境。

### 共用底層元件

```swift
struct RollingWindow<Value> { }
struct RollingMoments { }
struct RollingExtrema<Value> { }
struct LastEventTracker<Event> { }
```

- `RollingWindow` 保存固定長度環形資料。
- `RollingMoments` 保存合計與平方合計，供平均、變異及 Z 分數使用。
- `RollingExtrema` 以單調佇列提供滑動最高／最低值。
- `LastEventTracker` 保存最近事件種類、序號或距離，不保存整筆 Trade。

共用元件是實作工具，不直接暴露給買賣規則。正式規則只讀具名的領域屬性，避免字串 key、任意型別或未登記狀態。

### 領域 Context

```swift
struct SimulationRollingContext {
    var gradeLossCutPenaltyLevel: Int
    var tradingDaysSinceLastInvestment: Int?
    var lastWorseningBoundary: WorseningBoundary?
}

struct TechnicalRollingContext {
    // 實際欄位隨逐批技術任務加入，不預先建立未使用的通用集合。
}
```

`SimulationRollingContext` 先承接已有正式語意。`TechnicalRollingContext` 則只在對應 `tUpdate` 任務開始時加入該批窗口，不能先建立大量未驗證欄位。

### 需求登記

回溯服務不能只是把既有掃描包成下列介面：

```swift
context.searchPrevious(60) { trade in ... }
```

這仍會每天重新搜尋。技術需求應在重播開始前以具型別的固定需求登記，讓重疊窗口共用同一份序列，例如收盤價的 20／60 日平均與 125／250 日 Z 分數只推進一次當日收盤價。模擬需求則直接由正式規則所需的具名狀態組成，不提供候選任意新增永久 key 的介面。

## 初始化與每日順序

### 完整重播

1. 建立空 Context。
2. 依序把準備期 Trade 送入技術 Context。
3. 從正式模擬起始日開始，先計算當日技術值，再以模擬前態作決策。
4. 當日行動確定後，提交模擬事件並更新 Context。

### 局部重算

1. 由最早受影響日決定重算起點。
2. 技術 Context 最多讀取起點以前 250 筆必要序列一次。
3. 模擬 Context 分別取得最近完整賣出、最近加碼與最近惡化界線前態一次。
4. 後續全部逐日滾動，不重複查詢起點以前歷史。

### Yahoo 當日與 P10

1. 先建立不含當日假設結果的正式前態。
2. Yahoo 當日從正式前態建立一份 Context。
3. P10 的每個假設價格各自複製同一份正式前態。
4. 任一情境的技術值、買賣、加碼或 Grade 趨勢都不得寫回其他情境。
5. 正式行情恢復時重新從正式前態計算，不依賴最後一個 P10 情境留下的狀態。

## 251 筆前態風險

即時更新與 P10 目前只載入最近 251 筆 Trade。技術窗口足以由這些資料重建，但下列模擬事件不保證發生在 251 筆以內：

- 決定 G-M02 的最近一次非人工完整賣出。
- 決定 L-P10 的最近一次惡化預警或惡化確認界線。

如果事件早於 251 筆，完整重播與當日／P10 可能得到不同前態。建立模組前先執行 `RCTX-D01`，不能把固定 251 筆視為所有模擬 Context 的完整歷史。若確認有差異，優先以限定條件的起點查詢或可重建摘要修正，不為了省一次起始查詢就直接新增持久 schema。

## 任務清單

### 第一階段：`simUpdate` 試用

#### RCTX-D01：251 筆前態一致性診斷

- 類型：零修改診斷。
- 唯一問題：完整歷史與最近 251 筆是否重建出相同的 G-M02、L-P10 前態。
- 固定條件：現行 Baseline v16、`T2/S35`；不修改規則、不重播、不推進 T/S。
- 檢查：股票、窗口、日期、最近相關事件、完整前態、251 筆前態及差異集中度。
- 正向分支：若有差異，`RCTX-S01` 必須先加入正確的限定前態初始化。
- 反向分支：若零差異，仍不得把 251 寫成永久語意；模組保留可取得更早前態的初始化介面。
- 停止條件：資料不足以重建正式事件時停止，不以近似狀態代替。

**2026/08/30 完成：** 最近 251 筆不是安全的模擬前態界線。G-M02 在 A／B／C／D 共 12 個固定窗口中有 9 個日期狀態不同，集中於 Sample C 第三窗口中鋼；負損完整賣出距當日 251～259 筆。L-P10 在具完成後 phase 的 A／B／C／D 第一窗口與 A／B 九年路徑共有 2,960 個日期界線不同，其中 2,020 個日期可由 DecisionBase 決策預覽或當日無行動同態精確確認會改變 L-P10 輸入。C／D 第一窗口及 A／B 九年路徑的最後一日也各有一檔仍受影響。結論是 `RCTX-S01` 必須提供獨立的模擬前態初始化，不能直接把技術更新使用的 251 筆陣列當成完整模擬歷史；L-P10 的修正優先於純效能性的最近加碼改造。完整本機報告見 `exports/rolling-context-study/rctx-d01-251-t2s35-20260830/`。

#### RCTX-S01：建立 Replay／Simulation Context 骨架

- 新增預定檔案：`simStock3/RollingContext.swift`。
- 只建立生命週期、複製／分叉、Simulation 具名狀態與初始化介面。
- 先把既有 G-M02 局部變數移入 `SimulationRollingContext`，不改變初始化與每日更新語意。
- 不加入 `TechnicalRollingContext` 的實際指標欄位，不修改 SwiftData schema。
- 驗收：完整重播、局部重算、Yahoo 與 P10 的 G-M02 決策 Grade 與現行版本一致。
- 停止條件：若 P10 情境會污染正式前態，先修正分叉模型，不加入下一個狀態。

#### RCTX-S02：最近加碼冷卻改為滾動狀態

- 唯一變更：以 `tradingDaysSinceLastInvestment` 取代每個持股日最多 60 筆的反向掃描。
- 同時維持 A-E01 38 日、候選用 45 日及 S-T02 60 日的既有交易日語意。
- 自動加碼與有效手動加碼是否都屬於 `invested == 1`，完全沿用現行 `Trade.invested` 結果，不重新解釋規則。
- 新持股輪次、賣出、人工反轉與人工加碼重驗必須與現行掃描的中止條件一致。
- 驗收：逐日三個布林條件、加碼執行、賣出 gate、人工操作摘要與期末結果零差異。
- 停止條件：任何差異先定位計數邊界，不同時修改 38／45／60 門檻。

#### RCTX-S03：L-P10 惡化界線改為滾動狀態

- 唯一變更：以 `lastWorseningBoundary` 取代每日無固定上限的反向掃描。
- 遇惡化預警時保存「預警」，遇任一惡化確認分段時保存「確認」，其他階段沿用；當日本身仍在惡化預警或確認時不給 L-P10 恢復票。
- 驗收：逐日 L-P10 票、L 分數、L-T01 gate、成交路徑與期末結果零差異。
- 停止條件：若舊掃描存在不能由最近界線表達的語意，先修正狀態模型，不新增額外歷史陣列。

#### RCTX-S04：Simulation Context 整體驗收與效益量測

- 固定比較完整重播、由中途開始的局部重算、Yahoo 當日及十組 P10。
- 比較所有模擬欄位、Grade 趨勢、人工反轉、手動加碼、Stock 摘要及正式報告結果。
- 分別量測初始化時間、逐日 `simUpdate` 時間與總重播時間；不得只用理論複雜度宣稱改善。
- 若結果零差異但效益很小，仍可保留統一 Context 架構，但不得據此直接展開高風險 `tUpdate` 重寫。
- 完成本階段後才共同決定是否開始第二階段。

### 第二階段：`tUpdate` 分段導入

#### RCTX-T01：技術回溯基準量測與需求表

- 不改技術值，量測每檔每筆的窗口掃描次數、`tUpdate` 時間及 P10 放大倍數。
- 分開價格、一般技術值、成交量與 P10，避免只看到總時間而選錯熱點。
- 依實測決定 T02～T05 的實際順序；沒有可量測瓶頸的部分取消改造。

#### RCTX-T02：合格 TWSE 成交量窗口

- 先以 `TechnicalRollingContext` 維持最近 250 筆合格 TWSE 觀察序列，取代每日由當日倒找索引。
- Yahoo 列只讀取最近正式 TWSE 統計，不推進窗口；正式 TWSE 日才提交。
- 第一小步只改索引取得方式，平均、Z 與極值仍沿用原計算順序，先證明資料集合完全相同。
- 驗收：每筆合格索引與全部 `v` 欄位零差異。

#### RCTX-T03：滑動最高／最低值

- 依 T01 實測選擇九日技術極值或 125／250 日價格高低點先做。
- 使用單調佇列保存窗口極值；相同值的進出順序必須明確，避免窗口邊界差一筆。
- 驗收：所有受影響技術欄位逐筆零差異，P10 十組情境亦相同。

#### RCTX-T04：MA 與一般窗口合計

- 以環形窗口與合計取代 MA20／MA60 逐日重加。
- 浮點加減順序可能和原始由左至右重算不同；先在現有固定資料上逐筆比較原始值及規則門檻兩側距離。
- 若不能維持要求的精確度或導致任何規則分歧，停止本案並保留原掃描；不得逕自推進 T 版本接受差異。

#### RCTX-T05：125／250 日 Z 分數滾動 moments

- 這是預期效益最大、浮點風險也最高的一批，最後處理。
- 每一種資料序列分開導入合計與平方合計，不一次改完全部 Z 欄位。
- 明確處理零標準差、非有限值、暖機不足與移出窗口資料。
- 驗收除逐筆欄位外，還要比較所有 H／L／S／A 票、gate、成交與期末結果。
- 若零差異無法成立，必須回到舊計算或另提具 T 版本成本的數值語意變更，不把效能重構混成隱性資料規則更新。

#### RCTX-T06：P10 Context 分叉與整體效益量測

- 十個假設價格及正式恢復值都從同一份前日 `TechnicalRollingContext` 複製。
- 每個情境只加入自己的當日價格、成交量及衍生值，不能沿用上一情境的當日窗口結果。
- 比較 P10 顯示、正式 Trade 恢復值、Yahoo 當日與正常重播。
- 完成後重新量測全量 `tUpdate`、日常更新及 P10；只有實測改善才稱為效能成果。

## 驗收原則

- Context 重構預設是工程等價改造，不是候選回測；不得藉機修改規則門檻或解釋結果。
- 每個任務只替換一種回溯來源，保留舊實作作為同次對照，確認後才移除。
- Simulation 階段要求逐日決策狀態、人工操作與期末結果零差異。
- Technical 階段優先要求受影響持久技術欄位逐筆零差異；若浮點實作只能做到容差內一致，必須先暫停共同決定是否值得承擔 T 版本、完整重算與 Baseline 重建成本。
- 完整重播與局部重算必須在相同日期得到相同結果。
- Yahoo 與 P10 必須從正式前態分叉，且完成後正式資料不含假設情境殘留。
- 不新增 schema 欄位時，不因純等價重構推進 T/S；若任何持久結果或狀態語意改變，依正式 T/S 規則另案處理。

## 預定決策順序

1. 先核准並執行 `RCTX-D01`。
2. 依診斷結果修正或確認起點初始化設計。
3. 依 D01 結果先執行 `RCTX-S01`，再優先執行 `RCTX-S03` 修正 L-P10 前態，之後才執行純效能性的 `RCTX-S02` 與整體驗收 `RCTX-S04`；每項完成後停下回報。
4. 根據 Simulation 實測效益決定是否啟動 `RCTX-T01`。
5. T02～T06 依 T01 實測排序，不把本文件順序當成無條件授權。

### 範圍與版本結論

- 本階段只改變歷史前態的取得方式，不改變買賣條件、Grade／趨勢門檻或正式策略語意。
- 不新增 SwiftData 欄位，不推進 `T2/S35`，也不重建 Baseline。
- 單元測試另外覆蓋 251 筆技術視窗之外的認賠與惡化邊界種子、每日狀態更新，以及 P10 情境副本不污染正式前態。
- S02 與 T05-S1 都是工程等價改造；前者保存正式規則需要的模擬摘要，後者只合併既有技術窗口遍歷，不將候選數值或任意欄位加入 Context。
- Baseline 控制組若使用未辨識候選旗標，App 會立即拒絕；runner 現已提供明確 `--control` 模式，且畫面顯示失敗或沒有可靠產物時必須強制介入，不等待長逾時。

### 後續閘門

本輪 RCTX 工程到 `RCTX-T05-S1` 暫告一段落，目前沒有排隊中的核准改造。後續 `tUpdate` 或其他 `simUpdate` 回溯需求仍須由新的實測瓶頸逐項提出：先證明舊搜尋可由有限摘要等價表示，再加入對應 Context 欄位與零差異驗證；不得把 Context 擴張成未經檢驗的通用欄位集合。
