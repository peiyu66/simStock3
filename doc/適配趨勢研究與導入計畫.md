# 適配趨勢研究與導入計畫

## 目的與邊界

本計畫要建立「適配趨勢」：以現行 [Grade](選股評等.md) 背後的連續效率分數，描述一檔股票與現行策略的適配正在改善、穩定或惡化。它是 Grade 的時間方向，不取代 Grade，也不是另一組價格、成交量或基本面指標。

方向已確認；FT3 已在 Sample A 最早窗口找到 `wow` Grade 內可辨識且持續的改善／惡化方向，但尚未把趨勢用於任何規則：

- 研究階段只寫入 DecisionBase 的研究 SQLite；可以在 DEBUG／內部回測的 `simUpdate` 路徑加入讀取式 recorder，但不修改 SwiftData、`tUpdate`、正式規則或 `simUpdate` 結果。
- 適配趨勢來自策略模擬狀態，屬於 `simUpdate` 層，不得寫入 `tUpdate`。
- 只有它在相同 Grade、相同技術現象內提供穩定且有序的額外分辨力，才生成新規則。
- 交易規則只有在通過受控回測並正式採用後，才可讀取適配趨勢。另有一項受限例外：可依 [Grade 趨勢顯示導入計畫](Grade趨勢顯示導入計畫.md) 新增 SwiftData 最小狀態，僅供 UI 顯示與離線校正；仍須推進 S 並完整重播 `simUpdate`，不得因此視為交易規則已採用。

P6a 已完成；原 P6b 的事件反應與候選生成已整合進本計畫 FT5，不再另行執行。2026/08/15 已完成 FT0～FT4：Sample C 固定為 FT4 hash 順序前 20 檔，不再依 Grade、回撤或其他績效特徵篩選；原兩批各十檔只保留為隨機子群。候選完全凍結並進入 FT7 前，程式明示禁止建立或重播 Sample C。FT5-1／2／3 已分別停止 L-P06 量縮、L-P03 K 長短期低檔與 L-N02 同步破低，均未生成候選。本輪結論為暫不把適配趨勢導入交易規則；FT6～FT8 未啟動，研究程式與旁錄保留供未來不同樣本、窗口或 Baseline 重驗。

## 概念模型與既有資料

決策日使用與動態 Grade 相同的決策前截面：

```text
fitLevel = gradeEfficiencyScore
fitFast  = 20 個合格交易日的效率 EMA
fitSlow  = 125 個合格交易日的效率 EMA
fitTrend = fitFast - fitSlow
```

20／125 是第一個可驗證版本，不同時網格測試其他窗口。FT2 先檢查分布、暖機與噪音；若結構不成立，停止並重新提案，不以期末績效反覆調窗口。

資料全部來自現有 `Trade`：

| 資料類別 | 現有來源 | 新用途 |
|---|---|---|
| Grade 底層 | `rollAmtRoi`、`rollAmtProfit`、`rollAmtCost`、`rollDays`、`rollRounds`、`roi`、`days`、`gradeEfficiencyScore` | `fitLevel`、長短期適配趨勢 |
| 持倉狀態 | 庫存、`simDays`、`simUnitRoi`、買賣規則 | 區分累積適配變化與當輪暫時波動 |
| 證據強度 | 完成輪次、有效觀察日數 | `fitEvidence`；不直接決定買賣方向 |
| 診斷拆解 | `roi`、`days` 時間序列 | `roiTrend`、`daysTrend`，解釋變化來源 |
| 技術現象 | 現有 `t`／`v` 欄位 | 作為被適配趨勢調節的現象，不混入趨勢公式 |

每日規則只能讀取前一合格交易日結束後的 fast／slow；當日 `simUpdate` 全部完成後才更新當日狀態，供下一日使用。不得使用期末 Grade、當日行動後結果或未來賣出結果倒推。

## 研究 SQLite 與去重

DecisionBase 新增 `strategy_fit_observations`。主鍵必須包含 `window_id + stock_key + trade_date`：適配趨勢是 `simUpdate` 狀態，重疊窗口起點與交易路徑不同，不能像固定技術 observation 一樣跨窗口只按股票、日期去重。

同一窗口、股票、日期的 GRADE／H／L／S／A 事件共用一筆 observation，以 bridge 連到 `decision_events`，避免同日各 phase 重複保存。

至少保存：

- `fit_level`、`fit_fast`、`fit_slow`、`fit_trend`
- `fit_evidence_rounds`、`fit_evidence_days`、`fit_observation_count`
- `roi_trend`、`days_trend`
- `grade_name`、`grade_activation_passed`、`has_inventory`
- EMA 參數、schema 版本、有效性與有限值品質標記

研究資料只放在 `exports/backtest-decision-bases`，不進 Git 或使用者資料庫。

## FT5 候選規格

每條候選執行前必須固定：

- **唯一變因**：一個既有技術條件加一個適配趨勢區段；Grade、其他規則、資料、股票、窗口、本金、加碼與成本不變。
- **檢查項目**：直接票、gate、第一次分歧、後續路徑、Grade × 趨勢 × 窗口 × 股票、ROI、週期、輪次、資金與既有規則重疊。
- **正向分支**：方向可在未參與生成的窗口或 Sample B 重現，才進下一層。
- **反向分支**：若改善集中單股或單窗，先縮小／重寫假設，不直接進 Sample C。
- **停止條件**：觸發不足、高度重疊、方向無序、時間驗證反向且沒有可解鎖的原因，或已出現明確成果使後續候選意義重疊。

候選總數不超過三條，但同時只能有一條活動候選；第一個通過 FT5 的現象立即轉入 FT6，不繼續預先蒐集其他候選。FT5 失敗後只回報本項，是否投入下一現象另行討論。不為湊數放寬條件，也不把 fitTrend 當成連續權重任意調整多條規則。原 P6b 的事件反應與簡單候選生成已整合進 FT5，不再作為另一項重複任務。

## 正式 SwiftData 與交易規則導入邊界

交易規則的 FT8 只讀取正式採用規則計算下一日所需的最小狀態。顯示計畫可以先保存下列狀態，但只供 UI 與離線校正：

- `simFitFast: Double?`
- `simFitSlow: Double?`
- `simFitTrend: Double?`
- `simFitObservationCount: Int`

`fitLevel` 仍由 `gradeEfficiencyScore` 取得；`simFitTrend` 必須等於同列 `simFitFast - simFitSlow`，讓資料庫可直接匯出校正，同時保留可核對性。`fitEvidence`、`roiTrend`、`daysTrend` 預設只留研究資料。舊資料的新欄位先為 `nil`，不得把 0 誤認為趨勢穩定；完成 S 版重播後才可顯示。未來若交易規則正式採用，只能依決策前時序讀取前一合格交易日狀態。
