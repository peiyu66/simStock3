## 文件狀態的日常維護

這是任務進行中的工作程序，不是定期全庫掃描或背景排程。任務結案、規則採用／拒絕、方向停止／撤回／暫停、設計被取代或權威來源改變時，同步整理當次直接涉及的文件；準備 commit 或交接時補查同一範圍。狀態未變就沿用原紀錄，不反覆刷新日期。

1. **先核對依據。** 依正式決策、專題結論與完成證據判定，不因文件年代、檔名有「計畫」或長期沒更新就視為結案。證據不足時標示「待確認」及缺少的依據，不猜測完成或恢復執行。
2. **更新文件開頭。** 用短段落標明狀態、適用範圍、接續／現行來源及整理日期；已有清楚的狀態段就直接更新，不疊加多個「最新狀態」。日期區分事件發生與本次文件核對，不把整理日期當重新測試日期。
3. **同步索引與待續入口。** 本索引只保留狀態摘要及連結，不重抄版本、分數或證據表；目前進度與已授權待續另更新[工作交接](工作交接.md)。已停止或已完成的原提案移出現行待辦，但保留歷史條件與停止理由。
4. **保留歷史與定義。** 不刪正反證、授權演變、歷史版本與重現身分；原「未採用／未發布」可保留，但開頭須說明已被哪個結果接續。仍承擔現行定義的文件標為「現行定義兼歷史」，不能整份當舊計畫封存。交接歷史快照不可回寫，改由索引／現行交接補充。
5. **核對連結與界線。** 檢查本次修改的索引、來源、接續章節與被引用入口，確認沒有把舊狀態當現況。日常狀態整理不搬檔、不建立等候刪除區、不刪文件，也不自動重開研究、遷移資料或 commit／push。

狀態至少區分「進行中」「已完成／已結案」「已採用」「已停止／撤回」「暫停／暫緩」「已被取代」與「待確認」；混合文件按範圍說明，例如「部分採用、其餘停止」。**結案不等於採用，採用不等於發布；暫停也不等於結案。** 採用與正式版本仍以[現行回測規則](現行回測規則.md)、[Baseline 歷史](Baseline歷史.md)及[回測規則驗證](回測規則驗證.md)為權威，不另建立競爭的狀態或版本資料庫。

## 文件維護原則

- 使用者文件只在操作、畫面或使用限制改變時更新，不跟隨開發升版維護版號與逐版規則。
- 開發狀態於變更當次同步：目前版本、樣本與條件查[現行回測規則](現行回測規則.md)，歷次分數、報告與版本對應查 [Baseline 歷史](Baseline歷史.md)，實驗與採用理由查[回測規則驗證](回測規則驗證.md)。入口以連結取代重複摘要，歷史重現所需資料仍保留。
- 候選只有正式採用後才進入現行規則；未採用結果保留在驗證歷史與本機 `exports`。
- `exports` 是可重建或大型產生物，通常不納入 Git；長期有效的判讀寫回文件。
- 舊導入計畫可保留設計脈絡，但開頭應指向接續管理的現行文件，避免舊門檻被當成目前規則。
