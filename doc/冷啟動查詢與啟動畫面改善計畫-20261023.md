## 4. 索引與查詢計畫

實際持久副本只有：Stock 的唯一 `sId` 索引、Trade 的單欄 `stock` 關聯索引、MarketDay 的唯一 `dateTime` 索引。產品模型沒有明訂 `#Index`，也沒有窗口 projection 或關聯預取設定。

| 查詢形狀 | 目前對應 SQL 的計畫 | RAM 候選索引結果／決策 |
| --- | --- | --- |
| Stock 全表排序或 `group != ""` 排序 | `SCAN ZSTOCK` ＋ `USE TEMP B-TREE FOR ORDER BY` | `(group,sName)` 消除臨時排序，但仍是 index SCAN；不能聲稱已成範圍 SEARCH。現有約 0.075 秒不足以支持優先改造；predicate、來源拆分及索引均待實測成本支持，不要求先只返回 18 個模型 |
| Trade 整關聯 | `SEARCH ... ZSTOCK_INDEX (ZSTOCK=?)` | 本來已能定位單股，卻仍返回整股 2,141 列（代表股）；**有索引不會修好不必要的全關聯取回** |
| 最新／最早有效價、窗口 Trade | 只用 stock 索引，再日期過濾及臨時排序 | `(stock,dateTime)` 在 RAM 可 `SEARCH (stock=? AND dateTime>?)`，無臨時排序。首／末 query 代表股各回 1 列，窗口 1,227 列；查詢計畫未等於 SwiftData 實測 |
| 人工記號 OR 查詢 | stock 索引後過濾、日期臨時排序 | 去掉無用途排序；只取人工欄或 count／exists。若只在有責任的修復時執行，不優先為 77 列加兩組寬索引 |
| 最新官方價 | stock 索引後 source 過濾、日期排序 | 先用 `(stock,dateTime)`，量 source 過濾成本；只有證據顯示需要，才比較 `(stock,dataSource,dateTime)`，避免盲目堆索引 |
| MarketDay 同日／全庫 | 同日是 dateTime SEARCH；全庫是循 dateTime 索引 SCAN | 同日已適用；全庫問題是查詢範圍及時機，不能靠再加相同索引解決 |

P2 必須以 SwiftData 支援的 schema／`#Index` 路徑驗證關聯＋日期複合索引能否建立、舊庫能否安全開啟；本輪尚未編譯或遷移驗證。不在 App 管理的 SQLite 檔直接下 DDL，也不為繞過 API 限制先加冗餘股票 ID 欄位。擷取候選實際 SQL、`EXPLAIN`、返回／fault 筆數及冷開時間後才決定索引組合；保留索引建立首次成本、寫入成本、磁碟增加及還原相容性。

Apple 提供 [FetchDescriptor](https://developer.apple.com/documentation/swiftdata/fetchdescriptor)、[propertiesToFetch](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/propertiestofetch) 與 [SwiftData #Index](https://developer.apple.com/videos/play/wwdc2024/10137/)；這些是工具，不代替本案生成 SQL 與遷移驗證。`propertiesToFetch` 候選只用於純日期／摘要需求；顯示最新 Trade 的計算屬性若觸及未取欄位仍可能 fault，須實量。計畫術語依 [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)：SEARCH 與 SCAN、臨時排序各有不同含義。

## 5. 不再以上市例外或快取觀察重掃歷史

1. 首頁讀已保存的 `confirmedHistory` 與經 journal／來源身分驗證的 ledger 證據。完整性顯示所需的是「要求月份是否已確認」與「最新官方日」，不需要每次重驗全部留存價格。
2. 先直接採窗口內最新官方列與已確認月份。上市日／重新上市是否可縮短要求範圍，應在名錄上市日期異動、歷史匯入／更正、設定範圍改變或明確來源維護時計算；如需查較早價格，只做帶 stock／日期／來源／有效價條件的 exists／limit 1，保存已確認來源結果，避免未變動冷啟與回前景重做。
3. 優先重用現有 coverage／ledger 結構；若舊資料無法由既有證據判定，保持待確認，不擅自當完整，也不偷偷退回 `stock.trades.contains`。一次性來源銜接列為更新／維護責任、成功保存才完成；必要的最小來源證據格式變更在 P3 明列，不與「新增持久窗口摘要」混為一談。不得將一次性核對做成每次啟動的慣例。
4. 僅保存首末日期等小型記憶體結果，依 raw 插入／更正／刪除、股票日期設定、換群、匯入還原事件失效。未保存編輯也須同步失效；不能只等 didSave。即使原本窗口外的一筆被改到窗口內，也由寫入事件帶 stock ID 失效，不靠遍歷所有舊列觀察。
5. 不隨捲動保存。必要窗口內明細快取與首頁最小結果分開；保持新增資料、批次刪除、日期改正、存檔失敗後重試及跨 context 變更的[事件失效契約](更新檢查事件失效與盤中試算-20261023.md)。

### 6.1 P1a 的明確查詢契約與範圍

**現行狀態：低優先、依實測成本決定。**前次補強曾將 1,096→18 列為必要驗收；依本日使用者對 Stock 基本記錄量的確認，取消此硬門檻。保留具體候選作法供後續有成本依據時評估，目前可維持全名錄 Stock Query 後篩股群。

1. 若 `Stock.fetchGrouped(in:)`（目前 dataModel.swift 204）日後值得優化，可自建 `FetchDescriptor<Stock>`，predicate 為 `#Predicate<Stock> { $0.group != "" }`，sort 保留 `group`、`sName` 升冪。它可獨立評估，不要求同時拆首頁 `@Query`。
2. **只有決定縮小共用 Query 時，才需先拆分來源：**首頁 `stocks` 同時供 `catalogSearchResults`（viewList.swift 674）使用；直接加群組 predicate 會令未入群搜尋結果消失。目前保留共用來源；若之後有實測理由拆分，搜尋仍須保留 `group == "" && isListed`、多關鍵字皆須符合（每字可符合代號或名稱）、sId／sName 排序後最多 50 筆，以及單一精確代號／名稱「已在股群」提示（723）。篩選與排序必須在截取 50 筆之前；不能先截斷候選造成漏找。
   無論是否拆分，首頁原 sort、`groupedStocks` 同名時按 `sId` 的顯示次序及 SwiftData 反應式生命週期都保留；新增、刪除、空群→入群、入群→空群、群間移動及改名後，清單、搜尋結果與選取狀態仍須更新。
3. 18 是既有副本的股群成員數，用於驗證清單完整，不是 DB 返回模型上限，也不能寫成 `fetchLimit = 18`。保留 1,096 個 Stock 基本模型後再過濾可接受；不得因此展開未入群股票的歷史 Trade。
4. 不將群組 predicate 全域套到通用 `Stock.fetch`、`Stock.fetchAll` 或所有呼叫端。新增選股／搜尋仍可查未入群股票；`StockCatalogUpdater.apply` 仍比對完整上市名錄及標記已下市股票。精確代號查詢的正確性與首頁來源是否拆分是不同議題。
5. P1a 的採用依據是實際主執行緒耗時、重複 fetch、模型／fault 及排序成本；比較前後收益與來源拆分複雜度，不以返回 18 作通過條件。若採用 predicate，仍須用實際 SwiftData SQL／descriptor 核對；`group != ""` 可能 SCAN，縮小返回集合不等於 DB 只檢查股群成員。

## 7. 驗收矩陣與量測方式
