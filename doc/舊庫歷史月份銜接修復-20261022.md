# 舊庫歷史月份銜接修復

狀態：修復及隔離驗證完成，本機簽署準備中，尚未發布。來源主對話 `01a157c0-b093-70cf-8e24-55c477db90d7`；此案接續[更新週期計畫](更新週期與取消下載暫算計畫-20261021.md)，不改策略或計算公式。

## 問題與原因

升級後即使個股已有近期盤中資料，仍逐月向前下載六個月，並顯示大量待補月份。六個月批次上限本身沒有錯；舊版沒有逐月下載成功紀錄，新版把缺少 `twseHistoryCoverage` 解讀為所有月份尚未確認，卻漏了舊資料銜接。版本遷移沒有清空原始行情；盤中最新一筆也不能證明整段歷史完整。

原遷移驗證直接進入技術／模擬重建，沒有從啟動時的完整股價更新入口進入，因此漏掉來源排程。修正驗證必須包含 `updateDailyPrices → updateTWSEPrices → coverage → 排程／待補數字 → T／S`。

隔離的 14 股備份中，修前有 1,282 個月份未確認，各股首批會排出 2026/10 至 2026/05。這是測試副本的數字，不能說成使用者 iPad 上「903 個月」的逐筆驗證。

## 已採用的銜接口徑

使用者已同意只對舊資料作一次性相容處理：依目前能見窗口，把有效個股 TWSE 日期與已保存的正式大盤日期逐日比對。集合相同且參照非空的月份沿用；有缺日、缺正式參照或來源不合者仍未確認，不推測停牌，也不補造行情。

- 舊資料證據與實際下載成功紀錄分開，保存在既有 Data 欄位；不新增 SwiftData schema 欄位。
- 證據包含可用起訖日。第一個月只證明 `dateRequestStart` 之後；設定前移不能沿用這段以外的保證。
- 新建股票不走舊庫推定。一次銜接完成後，後續月份仍依實際下載確認；已有成功紀錄保留。
- 大盤只提供正式原始日期參照，無須先完成市場技術。缺大盤月份仍待補，個股 T 照既定獨立週期處理。
- 排程與待補計數共用 `unconfirmedHistoryMonths`；保存成功才使用銜接結果。保存失敗回復未提交證據並明示失敗；成功保存的先前月份不撤回。
- 刪除原始資料會撤銷相應月份證據，但不重新開啟舊庫推定；取消續批與重開後仍沿用已保存進度。

此方法無法發現大盤與個股恰好同時缺少同一日，這是使用者已知並接受的舊庫銜接限制，不宣稱等同原始下載收據。5 個不一致月份保留待查：2368 的 2016/07、2022/09；2449 的 2024/04；8454 的 2016/07；8467 的 2026/06。
