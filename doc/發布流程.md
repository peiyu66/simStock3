# 發布流程

## 目標

收到「push」後，優先使用 `scripts/push-release.sh` 完成固定檢查，不再把受限環境無法連線 GitHub 或讀取 Keychain 的結果誤判為憑證失效。

腳本不保存 GitHub token、Apple 密碼或簽署私鑰；GitHub 使用 macOS Keychain 中的 `gh` OAuth token，Apple 使用 Xcode 與 Keychain 現有的簽署身分。

## Git-only push

### 先做唯讀發布／結案核對

`python3 -B tools/check_release_closeout.py` 依 `release/closeout-profile.json` 的證據索引，核對本機 App/build、T/S、策略、完整規則 commit、發布 commit 與目前文件 commit；再核對所有指定樣本的固定／全期間報告、DecisionBase manifest／SQLite metadata／完成標記、Baseline 歷史分數及版本關聯、保存的發行 IPA／manifest、測試及人工操作遷移證據。它不重跑策略、測試或簽章驗證，也不啟動 App、修改資料庫、fetch、commit、push 或刪除檔案。

```zsh
python3 -B tools/check_release_closeout.py --json
python3 -B tools/check_release_closeout.py --online --json
```

預設完全離線。`--online` 額外實際下載公開安裝檔與網站（只在記憶體讀取）、核對 `origin/main` 及目前文件 commit 的 GitHub Pages 部署；須在已准許網路／既有 `gh` 認證的環境執行，不另登入。每項分 `passed`、`failed`、`unknown`（證據缺漏／未查）、`blocked`（操作不可用）。退出碼 `0` 表示全部通過，`1` 表示至少一項確定不符，`2` 表示尚不完整；離線即使 `offlinePassed: true`，整體仍為 `incomplete`，不能宣稱目前遠端已驗收。

索引只指向既有證據，不取代 manifest 或批准來源。採用／發布時更新其中身分及精確路徑，程式不寫死當期版本；不能為了通過而改寫舊證據。`ruleCommit` 定位 Baseline 規則、`releaseCommit` 定位實際發行來源、`--documentation-commit`（預設 HEAD）定位本次文件部署，三者可以不同但必須依序為祖先；發布後有 App／安裝內容修改便不能算已發布。`release/closeout-profile.json` 本身是證據索引，不屬安裝內容。大型本機證據仍不納入 Git；新 checkout 缺少證據時應顯示未知，不下載或重建補分。

合成負例測試：`python3 -B -m unittest discover -s tools -p test_release_closeout.py`。只用暫存小型 fixture，不讀正常裝置、不做 App build 或策略重播。正常裝置遷移仍須依當次授權另驗；隔離持久 fixture 成功不等於使用者資料已遷移。

### 限定範圍提交與隔離

下方發布腳本仍要求乾淨工作樹；存在其他任務差異時，不要全部 stage 或刪除來配合。先依已授權範圍精確提交，在乾淨隔離 checkout 執行需要建置的發布。純文件／研究工具整理可採限定 `git add -- <paths>`、commit 與普通 push；推送前查核**全部** `origin/main..HEAD` 的累積差異，不能只因最後一個 commit 是文件便判為 Git-only。有 App 改動時仍走完整發布，不以唯讀檢查器替代發布。

只有文件、工作約定、腳本或不影響 App 安裝內容的變更時使用：

```zsh
scripts/push-release.sh git-only \
  --message "Update release workflow" \
  --path AGENTS.md \
  --path doc/發布流程.md \
  --path scripts/push-release.sh \
  --path release/ExportOptions.plist \
  --path release/manifest.plist
```

腳本只 stage 明列的路徑；若仍有未 stage 或未追蹤檔案就停止，避免把其他工作一起提交。

## App 完整發布

會影響 App 程式、建置或安裝內容時使用。發布者須依變更選擇版本升級幅度，並明示資料重播範圍：

```zsh
scripts/push-release.sh app \
  --message "Show Grade fit trend" \
  --bump patch \
  --replay simulation \
  --path simStock3/StrategyFit.swift \
  --path simStock3/technical.swift
```

`--bump` 可用 `patch`、`minor`、`major` 或 `none`。只有版本已在本次變更中正確推進時才用 `none`。

`--replay` 可用 `none`、`simulation`、`technical` 或 `both`，分別表示不重播、`simUpdate`、`tUpdate` 及其下游、或兩者皆有規則變更。這是完成回報使用的明確聲明，不由檔名猜測。

資源受限的採用批次可指定 `SIMSTOCK_BUILD_JOBS`（預設1）、`SIMSTOCK_RELEASE_DERIVED_DATA` 與 `SIMSTOCK_RELEASE_WORK_ROOT`，把編譯並行數及建置／封裝產物納入當次監測；不省略測試、簽章或遠端核對。

App 模式固定執行：

1. GitHub API 與 Apple Distribution 身分檢查。
2. Fetch 並阻擋遠端領先。
3. 確認新 build 大於目前 `latest`。
4. 啟動 `simStock3 iPad 10.86 inch`，以非平行模式執行 `StrategyFitTests`、`RecalculationTests`；避免 Xcode 建立 Clone 後卡在 worker materialization／App launch 協調階段，讓單一基準裝置的案例進度與失敗可直接觀察。
5. Archive、匯出 IPA、核對 Bundle ID、版本、build 與簽章。
6. 產生 manifest 並計算本機 SHA-256。
7. Commit、push，核對遠端 `main`。
8. 覆蓋 GitHub `latest` 的 IPA 與 manifest，核對 GitHub 資產 SHA-256。

## Push 後資產上傳失敗

若程式已 push，但 IPA 或 manifest 上傳失敗，修正外部狀態後使用：

```zsh
scripts/push-release.sh release-only --replay simulation
```

此模式要求工作樹乾淨且本機 HEAD 等於 `origin/main`，會重新測試、封裝與上傳，不建立空 commit。

## 何時才需要使用者認證

腳本的 `gh api user` 只有在可存取網路與 Keychain 的環境仍失敗時，才代表 GitHub 認證可能真的失效。不得只因 sandbox 內的 `gh auth status` 顯示 invalid 就啟動登入。

Apple 簽署同理：只有正式發布環境仍找不到 Apple Distribution 身分，或 Xcode 明確要求 Apple ID、雙重認證、同意新條款或更新裝置註冊時，才請使用者介入。

## 執行權限

Codex 執行本腳本時，一開始就使用允許 GitHub 網路、macOS Keychain、Xcode signing 與 Simulator 的核准權限。不要先在 sandbox 試跑認證、簽章或發布命令。
